# ТЗ для GPT Luna — предварительный FIFO для себестоимости Ozon

Дата постановки: 22.11.2026. База аудита: main `b14658c80c9feef4f8595547eb489dde984cb59c`.

## 1. Результат для владельца

В карточке существующего дела FIFO открыть **«Предварительный FIFO»**, выбрать период и получить оценку себестоимости выкупленного товара с видимыми допущениями. Для текущего сценария достаточно уже имеющихся ведомостей: отдельно за день снимка и за последующий период. Бот предложит использовать уже импортированные документы или загрузить их штатным способом. Поиск поставок по всей истории и ручная разметка тысяч отправлений этому пути не нужны.

После загрузки достаточной детализации бот может повторить движения по порядку и оценить себестоимость конкретных выкупов. FIFO сам назначает стоимость по очереди доступных поступлений. Физическая маркировка упаковок по партиям для этого не требуется. Связь с отправлением нужна, чтобы перенести уже назначенную стоимость из доставки в продажу или вернуть её при отмене/возврате.

Расчёт явно показывает, какие числа взяты из отчёта, какие подтверждены владельцем как исходные сведения и какие являются допущениями. Владелец может сохранить выбранный расчёт отдельным снимком. Сохранение, подтверждение и повторное открытие такого расчёта не активируют очередь, не добавляют движения в фактический FIFO и не меняют основной отчёт прибыли. История и ранее сохранённые сценарии сохраняются.

### Что входит в первый выпуск

- Один магазин, одна карточка дела, один точный SKU, одна подтверждённая ставка старой партии и одна ставка новой. Складской периметр — общий пул FBO SKU по всем складам из согласованных отчётов. SKU разных карточек, магазинов и схем не складывать. Если владелец хочет очередь отдельно по складам или переход между тремя ставками, текущий сценарий сообщает об ограничении.
- Расчёт в продаваемых упаковках. Количество поставленного товара и количество единиц внутри упаковки — разные величины.
- Сводный сценарий по ведомостям, хронологический сценарий по событиям, сохранённые оценки, сравнение оценок и отдельная условная прибыль при сопоставимой финансовой базе.
- Существующая кнопка проверки готовности фактического FIFO остаётся самостоятельным путём по Decision 066. Никакого переноса предварительных событий и стоимостей в фактический журнал, Period Profit, Return COGS, действующие ставки, ценообразование, сохранённые планы и выгрузки фактической прибыли.

Вне выпуска: расширение автоматического обхода архива поставок, новые живые запросы Ozon, массовый пересчёт других SKU, распределение налогов по товарам, замена фактической истории приближённой.

## 3. Данные, даты и безопасные границы

### 3.1. Скоуп и версии

Один неизменяемый контекст входа: owner / tenant, store, product identity, SKU, offer (когда известен и подтверждён), case ID, ревизия дела, timezone, версия схемы предварительного расчёта, версия политики FIFO, отпечатки выбранных доказательств и допущений. При смене владельца, магазина, SKU, ревизии, файлов, периода, timezone, ставки или допущения старый предпросмотр становится устаревшим. Нельзя применять документы из соседнего дела, даже если артикул выглядит одинаково.

Считать даты в timezone магазина. Снимок — включительный конец даты D, период движений — от D+1 до выбранного конечного дня включительно. Временная граница — 00:00 следующего местного дня. Входной timestamp без смещения допустим только с явной известной/подтверждённой зоной источника. Если локальное время неоднозначно или не существует, требуется однозначное смещение. Дата в имени файла — предложение, пока текущий импорт не подтвердил период. За дату приёмки не брать дату создания акта, заявки, расписания, смены произвольного статуса или дату отправки поставщиком.

Количество — целое неотрицательное число, boolean отвергать. Отсутствие отдельно от явного 0. Денежные поля — `Decimal` с правилами нормализации существующего FIFO, вычислять без float, округлять конечные суммы до копеек согласно существующему `ROUND_HALF_UP`. Допуск суммы движений для сводной оценки — 0 упаковок. Частичность другого источника показывать отдельно, без прибавления недостающих единиц.

### 3.2. Снимок доступности

Из колонки конца дневной ведомости D взять все восемь категорий: `available`, `expiring`, `defective`, `checking`, `internal_transfer`, `seller_withdrawal`, `buyer_return_transit`, `buyer_delivery`. Сверить каждую с категорией начала ведомости D+1. Равенство только общей суммы недостаточно. Проверить внутренний баланс обоих отчётов и совпадение периметра. Если точного однодневного отчёта пока нет, показать какие даты нужны; периодный отчёт может быть самостоятельным контролем, но не заменяет выбранный снимок в V1.

Для кейса, где старой партии вне учёта Ozon не оставалось и новая до конца D не принята, весь начальный итог является исходным старым товаром модели только после явного подтверждения этих условий владельцем. Ненулевая приёмка в отчёте D не устанавливает сама по себе партию. Если состав начального остатка смешанный, простой сценарий недоступен; не угадывать долю по ставкам. Готовящееся к продаже, резерв и товар в приёмке, которых отдельной строкой в отчёте нет, показывать как неизвестные. Сохранять пояснение даже при совпавших итогах.

Для хронологической очереди `available` — начальный доступный слой. `buyer_delivery` — отдельный резерв ранее переданных отправлений по старой ставке. Другие категории — удержанные единицы. Отдать их в доступный слой можно только отдельным связанным событием освобождения, подтверждённого пригодного возврата или перемещения. Число на приёмке новой поставки не прибавляется к доступному остатку. Отдельный товар дома отображается по делу, в расчёт FBO включается только после подтверждённого поступления.

### 3.3. Статусы результата

| Статус | Значение и UX |
| --- | --- |
| `NEED_INPUT` | Нет требуемого отчёта, ставки, периметра или подтверждённого допущения. Показать точный недостающий шаг. |
| `SOURCE_CONFLICT` | Неподтверждённый баланс, категории на стыке различаются, активные версии одного окна конфликтуют либо модель даёт невозможные количества. Денежного итога блока нет. |
| `SUMMARY_RANGE` | Допустимый диапазон по суммарным движениям и явно указанному диапазону остатка старой партии. Поштучной привязки нет. |
| `TIMELINE_MODEL` | Последовательность полностью пригодна для воспроизводимого предварительного прогона; значения остаются модельными. |
| `TIMELINE_GAP` | Нехватка/коллизия последовательности. Независимая сводная оценка, если доступна, остаётся на экране; траекторию до первого пробела можно показать только отдельным счётчиком покрытия. Целую оценку по датам она не заменяет. |
| `STALE` | Источники или активное дело изменились. Предложить новый расчёт; историческую сохранённую оценку можно прочитать с её прежними входами. |

Не использовать статус `READY`, `APPLIED`, `CONFIRMED` или `COMPLETE` фактического FIFO для результатов этого экрана. Сравнение предварительных моделей проводится независимо от того, разрешён ли фактический расчёт.

## 4. Сводная оценка по двум отчётам

### 4.1. Входы

- A — старые упаковки во всех категориях на начало D+1 (итог снимка после подтверждения состава).
- L — приход из принятых поставок, колонка L за период. В V1 владелец подтверждает гипотезу **«Весь приход из поставок в этом окне относится к новой партии»**. Это возможно даже при неизвестном размере всей закупки. Значение L берётся из ведомости; план поставки, акт с неопределённой датой и ручной общий итог не заменяют его. Для этого сценария неизвестная доля старых поступлений — отдельный запрос подтверждения, не ноль.
- R — приход от покупателей, колонка M (брутто вклад в остаток). В модели неизвестная старая часть может быть от 0 до R. Для V1 положительные N–R, кроме уже отделённого M, и положительные U/Y/Z требуют отдельной классификации, поэтому показывать сводный контроль без денежного сценария. Исключённые из товарного баланса S/AA показывать как компенсации, без повторного учёта в количестве.
- S — выкуплено, колонка T периода. CSV с отличающимся количеством показывает свою дельту отдельно. Сводная модель использует S из ведомости и не присваивает ошибку произвольной строке CSV.
- D — остальные поддержанные выбытия V/W/X. Старая часть может быть от 0 до D. Выбытия не включать в себестоимость выкупов.
- B — общий остаток на конец периода, колонка AM.
- `o_min, o_max` — нижняя и верхняя границы старого остатка на конец по всем категориям. По умолчанию неизвестен: `[0, min(B, A + R)]`, выводить «остаток старой партии не установлен». Владелец может задать диапазон или одно число как гипотезу, после предпросмотра. Частичное наблюдение о старых упаковках в доставке показывает только видимое количество с оговоркой; его нельзя молча установить и нижней, и верхней границей. Ограничить диапазон `0 <= o_min <= o_max <= min(B, A+R)`.

### 4.2. Формула и проверки

Проверить `A + L + R - S - D == B`. Для возможного распределения `r_old ∈ [0,R]`, `d_old ∈ [0,D]`, `o ∈ [o_min,o_max]`. Тогда `sold_old = A + r_old - d_old - o`, `sold_new = S - sold_old`. Итоговый диапазон целых количеств:

```text
sold_old_min = max(0, A - D - o_max)
sold_old_max = min(S, A + R - o_min)
sold_new_min = S - sold_old_max
sold_new_max = S - sold_old_min
gross_cogs_at(n) = n × old_cost + (S - n) × new_cost
cogs_low, cogs_high = sort(gross_cogs_at(sold_old_min), gross_cogs_at(sold_old_max))
```

Пустое пересечение выдаёт `SOURCE_CONFLICT`. При росте новой ставки денежные границы автоматически меняются местами. Денежный результат — **себестоимость выкупленного товара до сторно возвратов**. При чтении диапазона пояснить, что это две связанные пары распределения, и нельзя одновременно сложить оба минимума. Не выводить среднее как рекомендованную точную сумму. Это модель по сумме отчетного окна, она не восстанавливает внутридневной порядок или дату исчерпания слоя.

## 5. Хронологический сценарий

### 5.1. Источники и нормализация

Опциональная кнопка `Добавить CSV отправлений FBO` открывается из предварительного сценария. В V1 читать UTF-8 с необязательным BOM и разделителем `;`; допустимы дополнительные колонки, их значения не выводить и не хранить. Обязательные колонки: номер отправления, SKU, количество, статус, фактическая дата передачи в доставку, дата доставки. Если артикул указан — сверить его с точным SKU активного дела. Времена и семантику колонок фиксировать на экране предпросмотра. Дату оформления, запланированную отгрузку и финансовые даты нельзя использовать вместо фактической передачи. Статус «Доставлен» с датой доставки участвует в сверке выкупа; для статуса «Отменён» факт доставки не выводится одной заполненной датой. Результат считывания содержит явный период пригодности и дельту к ведомости в штуках.

Взять лимиты проекта: вход до 10 MiB, до 50 000 строк и 1 000 000 единиц после фильтрации точного SKU. Отсечь файл по размеру до скачивания и проверить повторно после чтения. Перенять ограниченную обработку существующего FIFO report worker; выделить собственный тип импорта, отдельный от строгого формата `physical_sales` и legacy CSV себестоимости. До завершения операции иметь один активный ещё не подтверждённый импорт на владельца и дело, конфликт чтения — безопасное сообщение. Ошибки отображают тип проблемы и агрегат, не сырой ряд, ID, имя или адрес. Повторное чтение тех же байтов идемпотентно. Две противоречащие строки по ключу `posting_number + finance_sku` в одном наборе блокируют хронологию. Противоречивые источники нельзя склеивать по дням или похожим количествам.

Принятые поступления, пригодные возвраты, вывозы, списания и освобождение удержанного остатка читаются из существующих точно связанных документов FIFO, если они доступны. Для доступных владельцу подробностей, которых нет в штатных документах, предусмотреть **отдельный опциональный шаблон** `docs/templates/fifo_provisional_movements_template.csv`. Владелец вводит только известные дополнительные движения; строки отправки и выкупа массово берутся из CSV Ozon. Шаблон и импорт имеют собственный тип, те же ограничения и предварительное подтверждение. Данные такого импорта пригодны только для модели и отмечаются как ввод владельца. Живой коннектор для этого не нужен.

Заголовок: `event_kind;event_reference;effective_at;sku;quantity;posting_number;stock_zone;resellable;source_reference`. UTF‑8/BOM; timestamp ISO 8601 с явным смещением или заранее подтверждённой зоной. `event_reference` — уникальный безопасный ключ внутри набора, `source_reference` — обязательная ссылка владельца на строку документа, из которой он взял движение; произвольный текст и URL запрещены, длина до 100 символов. Допустимые события: `SUPPLY_RECEIVED`, `OPENING_TRANSIT_LINK`, `NON_BUYOUT_RESTOCK`, `SALE_RETURN_RESTOCK`, `RELEASE_HOLD`, `NON_SALE_REMOVE`. Для привязки стартовой доставки и двух возвратов требуется номер отправления. Для освобождения/списания требуется одна из зон снимка либо доступность; для поступления зона обязательна, `available` означает фактическую доступность. Для двух возвратов требуется явное `resellable=true/false`. Для каждого типа позволять только применимые поля. Привязка стартовой доставки относится к началу модели, проверяется по передаче до D+1 и исключается из дальнейших событий расхода. Она не может одной галочкой подтвердить весь резерв. Чистые аналоги именованных полей в имеющихся документах нормализовать в эти же события без повторного расхода. Конфликт файла и сохранённого источника по одному событию блокирует хронологию.

Если имеющийся тип источника не несёт фактического времени или связь с исходной операцией отсутствует, он остаётся диагностическим источником. Бот показывает пробел и оставляет независимый сводный результат. Для приёмки успешной хронологии использовать связанный синтетический набор этих же контрактов через обычную загрузку Telegram и безопасное подтверждение: тест одной чистой функции недостаточен.

### 5.2. Нормализованные события и алгоритм

Модель — конечные доступные слои по FIFO и отдельные журналы резерва по точному ключу отправления, уже выкупленных аллокаций и удержанных зон. Очередь сортируется по подтверждённому времени/порядку поступления. Возвращённые пригодные единицы восстанавливаются с исходной ставкой и приоритетом исходного слоя. Раздельные аллокации хранят целые количества и сумму; исторические слои недоступной зоны не подменять бесконечной ставкой.

| Событие | Правило |
| --- | --- |
| `SUPPLY_RECEIVED` | Конечный слой по новой ставке только на фактически принятое и доступное количество. Приёмка/проверка до доступности остаётся в отдельной зоне, если это различие видно в источнике. |
| `OPENING_TRANSIT_LINK` | Связать подтверждённое отправление, переданное до D+1, с отдельным начальным резервом по старой ставке. Сумма ссылок не больше `buyer_delivery`; неизвестные единицы остаются неразмеченными в этой категории. |
| `BUYER_DISPATCH` | Снять количество с доступных слоёв FIFO и записать назначение в резерв. Денежная себестоимость выкупа на этом событии равна нулю. Повтор не расходует запас. |
| `BUYOUT` | Списать из резерва именно его аллокацию один раз; это брутто себестоимость выкупа. При неподтверждённой связи с резервом — пробел. Отмена после выкупа требует события возврата с отдельным подтверждением. |
| `NON_BUYOUT_RESTOCK` | До выкупа вернуть пригодные единицы из резерва с той же ставкой только по факту возврата в продажу; товар в пути или на проверке остаётся удержанным. Повтор и превышение остатка резерва блокируются. |
| `SALE_RETURN_RESTOCK` | Привязать к выкупу. Для частичного возврата из нескольких ставок восстановить последние списанные единицы первыми по ранее принятому правилу. Не больше ещё не возвращённого количества. Если товар непригоден, доступная очередь не пополняется. Финансовое сторно возвращённой себестоимости отдельно от физического возврата и только на подтверждённой финансовой стороне. |
| `RELEASE_HOLD` | Перевод известного количества из проверки, перемещения или начального возврата в доступность с исходной ставкой. Для `buyer_delivery` использовать переход отправления. |
| `NON_SALE_REMOVE` | Подтверждённый вывоз, списание или утилизация уменьшает соответствующую категорию. Для доступного общего пула с подтверждённым местом моделировать расход по FIFO; из удержанной зоны с неизвестной исходной стоимостью — пробел. Стоимость вывести отдельно, не в брутто COGS выкупов. |

Хронология пускается от D+1 до конца окна и проверяется по двум балансам: сохранение общего количества и совпадение восьми категорий с наблюдениями там, где у события подтверждён тип. Не продолжать расчёт в минус. Повтор, перекрытия, невозможные статусы, пропущенное фактическое время и пропущенное поступление расходуются как отдельные причины неполной хронологии, а не компенсируются фиктивной приёмкой. Если события одной группы времени взаимозаменяемы, допускается стабильный порядок по нормализованному ключу. Если перестановка изменяет стоимость или доступность, а порядок источником не доказан, выдать `TIMELINE_GAP`; консервативная первая версия допускает отказ для любого спорного равенства времени при изменении одного резерва или общей очереди. День с отчётным агрегатом нельзя разрезать на выдуманные события.

Для результата `TIMELINE_MODEL` сверить число брутто выкупов с S, поступления и несбытовые движения с соответствующими категориями и открытие/закрытие с документами. Для каждого используемого набора явно указываются период, периметр и подтверждённая владельцем полнота именно для моделируемых типов движений, включая незавершённые отправления и изменения доступности. Остаток непривязанного начального резерва допустим лишь как неиспользованная отдельная категория, которая сходится в конце; ему запрещено покрывать неизвестный выкуп. Схождение итогов само по себе не заменяет ни покрытие, ни цепочки событий. В текущем кейсе CSV даёт +1 за конец окна и +3 до 15 ноября, поэтому эти файлы показывают полезное покрытие и сводную оценку, а не полноценный хронологический результат. Известные 1 319 старых доставок — часть операционной сверки, они подтверждают стоимость для этих отправлений по исходному событию; агрегат S не корректируется простой подстановкой количества из CSV.

## 6. Сумма прибыли и хранение расчёта

### 6.1. Условная прибыль

На первом PR показать диапазон себестоимости и управление предпосылками. Итог прибыли включить в заключительном PR по следующим правилам.

Для экрана варианта владелец может указать **базу до товарной себестоимости и до налога**. Бот показывает SKU, период, рубли и периметр «выкупленные единицы до сторно» и требует явного подтверждения, что цифра сопоставима. Это расчёт `P_before_tax_min = base - cogs_high`, `P_before_tax_max = base - cogs_low`, со статусом «Условная прибыль до налога». База может быть и отрицательной. Если известна только общая прибыль магазина, другой период, выручка по дате начислений с несовпадающим набором выкупов либо сумма после списанной себестоимости, она не является подходящей базой. Ничего из этого бот не подставляет автоматически.

Автоподстановка допустима только из уже доступного на чтение точного снимка, если подтверждены совпадение SKU, валюты, периметра и идентичности событий, а финансы по нему уже отдают сумму в том же определении. При несовпадении или отсутствии точной связи оставить только отдельный ввод для условного расчёта. Налоги и сторно фактического отчёта не пересчитывать по этому сценарию. Уточнение после налога — отдельный контракт с `TaxService` и отдельным подтверждением, вне этой задачи. Показывать на экране брутто COGS, допущение по возвратам и отсутствие сравнимой базы, когда она недоступна.

### 6.2. Сохранение, изоляция и сравнение

- Предпросмотр сначала только на чтение. Короткоживущий callback с TTL 15 минут привязан к owner/store/SKU, case ID, case revision, exact fingerprint входов, версии сценария. Использовать opaque ticket из runtime. После повторного чтения актуальных доказательств кнопка **«Сохранить оценку»** добавляет только отдельную неизменяемую запись. Двойное нажатие/повтор запроса возвращает тот же результат по idempotency key. Обновление предпосылок создаёт новую оценку.
- Таблица `fifo_cost_provisional_previews` в отдельном добавочном шаге схемы FIFO: scope/identity, case ID/revision, immutable id, created_at_utc, version, input fingerprint, idempotency key, bounded JSON итогов/предпосылок и ссылки на неприватные идентификаторы evidence. Ключ идемпотентности уникален в scoped case. Новая таблица прошивается через существующий repo, миграцию и снимок/восстановление. Поля группировать в существующий стиль project migrations, следующий номер взять от актуальной ветки (на базе схемы v19 — v20). `PRAGMA user_version` владельца Planning Workspace оставить прежним. Максимум 100 записей на дело, до 64 KiB на сериализованный результат; при превышении отказывать без тихого удаления.
- В таблице нет сырых CSV/XLSX, адресов, номеров заказов, комментариев, buyer PII и аллокаций с реальными идентификаторами. Оперативный разбор CSV остаётся в ограниченном worker/контексте запроса. Временное сопоставление ключей внутри одного прогона можно не сохранять; для долговременных отпечатков использовать хэш входа и существующий scoped digest, без внешних логов и без пересказа содержимого.
- После перезапуска доступно агрегированное сохранённое значение. Если источники изменились, экран показывает «Сохранённая оценка по прежним данным» и кнопку нового расчёта; сравнение не заменяет текущий счётчик.
- Сравнение разрешено между двумя оценками одного store/SKU, той же валюты, периода, метода и основы S с одинаковой политикой FIFO. Для сравнения прибыли дополнительно совпадает денежный периметр, стадия налога и сторно. Если источники различаются, разницу в покрытии показать; при неполной сопоставимости вывести обе карточки по отдельности без общей дельты. Разницу интервалов вычислять как `[new_low - old_high, new_high - old_low]` и подписать «возможная разница», без причинного утверждения.

| **PF25** | Руководство, текущий статус, карта тестов и CHANGELOG. Архитектурное решение описывает именно добавленную границу между оценкой и фактом. Заполнить проверочную матрицу и список остающихся дыр по данным. |
| **PF26** | PR C: раздельные CI для точных SHA всех зависимых PR, пакет независимого review, известные ограничения и рабочая команда для проверки. |

После каждого этапа в журнале указать выполненные файлы, точный commit/branch (если зафиксирован), выполненную команду и результат, смысл проверки и что не проверялось. В Resume: последний готовый PF, следующий PF, зависимости и SHA текущих PR, незакрытый blocker (если есть). После сокращения контекста читать журнал и проверять фактическое состояние. Неполнота истории данных владельца блокирует хронологический результат для этой истории, но не этапы разработки, синтетическую приёмку и сводную оценку.

## 10. Верификация, выдача PR и ограничения выполнения

- Изолированные worktree/checkout. Синтетические fixtures и временные базы. Не брать пользовательские `data/`, Downloads, `.env`, реальные ID, рабочие XLSX/CSV и секреты в Git/артефакты. Не запускать production бота, не отправлять реальные запросы в Ozon/Telegram и не менять цены или сделки. Не сливать и не развёртывать.
- Каждый PR: профиль собственных тестов и соседних FIFO/CSV/Telegram/Period Profit, полный `pytest` в изолированной среде, `compileall`, `git diff --check`, сравнение исходных хэшей `data/`. Прошедший CI должен относиться к проверенному SHA, по которому выдаётся PR. Для CI использовать текущий Windows/Linux Verify и Docker smoke проекта.
- Review packet каждого PR: точный SHA и база, границы реализации, затронутые файлы, команды и результаты тестов, скрин/текст синтетического Telegram прохождения без данных владельца, таблица рисков и регрессий. Отдельно показать, что никакая ветвь предварительного сценария не пишет в фактическую историю и что работа операционных CSV/legacy стоимости не изменилась.
- Остановиться с вопросом владельцу только при новом бизнес-решении, которое меняет оговорённый периметр, или при блокирующем доступе. Отсутствие новых документов для реального кейса не повод откладывать независимые этапы. В конце выдать три готовых зависимых PR с зелёным CI и пакет независимого review.
