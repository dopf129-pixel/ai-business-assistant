## Итог аудита

Новая функция должна расширять существующие `UnitPriceScenarioService`, `UnitPriceScenarioSource`, `PlanningWorkspaceRepository` и наблюдения, а не создавать второй финансовый или ценовой движок. Сейчас модель одной успешной продажи считает базовые компоненты и опционально доказанный кросс-докинг. Это **не полный P&L SKU**: хранение, потери возвратов/невыкупов и часть рекламных расходов пока не представлены как доказанные повторяющиеся расходы на успешно сохранённую единицу.

Публичный сценарный расчёт вызывается из кнопки `unit_economics` через `AssistantButtonHandlerService` и `TelegramUnitPriceCalculatorRuntimeService`. Сценарный snapshot собирает `UnitPriceScenarioSource`; чистую арифметику выполняет `UnitPriceScenarioService`. Из сохранённого FBO-плана уже можно начать owner-confirmed price observation через `TelegramUnitPriceObservationRuntimeService`; отдельного flow ценового эксперимента со сменой baseline/candidate ещё нет.

## Карта lineage

|---|---|---|---|
| Товарная идентичность | `ProductService.load_products`; catalog row `product_id`, `offer_id`, `sku` | Сценарий требует ровно одну строку по SKU и сверяет product/offer identity. Смена tenant/store меняет scope | `UnitPriceScenarioSource`; это ключ сопоставления товара, а не финансовое доказательство |
| Цена продавца и комиссия | `OzonClient.get_product_prices(product_id, offer_id)` через `CurrentProductEconomicsSource.get_price_and_commission_facts`; точечный текущий снимок | FBO-комиссия из текущей карточки; текущая цена продавца `marketing_seller_price` с fallback на `price`. Не историческая цена продажи и не доказанная ставка на любой будущей цене | Текущий сценарий цены; price-band и manual tariff profile разрешаются существующим `UnitPriceTariffResolver`/frozen tariff snapshot. Вне известного диапазона ставка неизвестна |
| Себестоимость | Tenant `ProductCostService.get_cost(product_id)`; current row и `updated_at`. Для периода есть отдельный `get_historical_cost_evidence(at_date, identity...)` с effective-dated history и ограничением ретроактивности | Текущий сценарий привязан к одному product ID и валюте RUB. Периодный COGS доступен только по подтверждённой временной записи/идентичности; отсутствие истории не равно нулю | Сценарий калькулятора и `PeriodProfitEffectiveCostService`. Не переносить текущую стоимость на прошлые фазы без даты действия |
| Налог | Настроенная политика активного магазина из `TaxConfigurationService.get_policy`; актуальный снимок | Store-scoped policy; заданный налоговый режим/ставки должны быть полными. Не источник правовой консультации и не налоговая история | Существующий `TaxService` внутри canonical forward расчёта. Расширенные расходы при режиме «доходы минус расходы» должны попасть в taxable gross profit до `TaxService` |
| Баллы за скидки | `FinanceService.get_daily_discount_points_evidence` по `/v1/finance/accrual/by-day`; `accrual_date`; точный finance SKU внутри posting | Current scenario агрегирует 28 завершённых календарных дней; положительная sale amount, бонус не выше суммы продажи, дедуп по `posting_number + finance_sku`, конфликт/неполный день блокирует результат. Это взвешенная доля начисленных баллов от продаж, не будущая гарантия | `UnitPriceScenarioSource`/`UnitPriceScenarioService`; влияет на существующую налоговую базу. Остаётся отдельным от расходов и от фактической будущей скидки |
| Финансовые начисления и fee categories | `FinanceService.get_daily_finance` и accrual type dictionary по дневным финансовым начислениям; фильтр — accrual date | SKU-фильтр допускает строки, где SKU найден в posting products или item fees. Product commission/services фильтруются по SKU, но `net_accrual` берёт `total_amount` всей совпавшей начисленной операции. На multi-SKU posting нельзя считать этот total целиком затратой одного SKU | `PeriodProfitQueryService`, экспериментальная экономика периода, finance detail/attribution. Нужны leaf-level ownership и exact SKU match; общий/неразнесённый остаток не становится ставкой на SKU |
| `sales_count` из finance | Положительные `sale_amount` внутри matching posting product row | Инкрементируется на один финансовый product-row с `sale_amount > 0`; поле не умножается на `product.quantity` и не доказывает количество успешно сохранённых единиц | Может служить числом финансовых строк/наблюдений в соответствующем legacy average, но не `Q_retained` и не denominator нового strict unit model |
| Реклама по финансовым начислениям | `fee_breakdown` от accrual rows + явно разрешённое owner mapping operation names | Период accrual-date; SKU только если операция явно item/SKU-attributed и источник полный. Campaign/account-level totals не распределяются автоматически | Period report и `PeriodProfitQueryService._expense_evidence`. Возможна роль primary только с доказанным охватом и отсутствием перекрытия с другими источниками |
| CPC Ozon Performance | Существующий `advertising_service.load(date_from, date_to, {sku})`; report-date | Отдельный SKU-сопоставленный CPC source со своим completeness/датой отчёта. Не все рекламные типы и не обязательно тот же временной cohort, что FBO posting/accrual date | Observation evidence/сверка; CPC из Performance и финансы — альтернативные представления одного spend, не две суммы. CPO/другие типы требуют отдельного доказанного coverage |
| Возвраты и невыкупы — событие/количество | `ReturnsBuyoutFactsSource`: FBO postings по since/to, product SKU/offer, quantity и текущий статус; Returns API FBO страницы до лимита, события привязаны к posting | Posting statuses — снимок на момент запроса. Return API classification различает `ClientReturn` и `Cancellation`, причины отказа и неизвестные причины; неполные страницы, неоднозначная отмена или не terminal status блокируют ready estimate. Для наблюдения доставленные + подтверждённые customer non-buyout — модельная оценка выкупа с выборкой, не Premium Analytics и не строгая связь фактического возврата с каждой delivered единицей | `ReturnsBuyoutAnalyticsService` и observation collection. Возвраты учитываются отдельными единицами; нельзя автоматически вычитать все возвраты окна из доставок того же окна как одну когорту |
| Финансовые потери возврата/невыкупа | `ReturnsFinanceAttributionFactsSource` связывает event с finance accrual по `posting_number` и finance SKU; `ReturnsFinanceAttributionAnalyticsService` классифицирует начисления | Требуются полные Returns и finance дни, совпадающие posting/SKU, отсутствие multi-product attribution ambiguity. Наблюдаемый net amount по событию не равен автоматически расходу на одну сохранённую продажу | Period return-finance analysis. Для новой модели расходы должны быть разложены на уникальные signed subcomponents, связанные компенсации вычтены, знаменатель строго доказан отдельно |
| Возвратный COGS и восстановление товара | `PeriodProfitReturnCOGS*` evidence/readiness/authorization/commit chain; `ReturnInventoryRecoveryRepository` | Recovery может зависеть от статуса/пригодности/подтверждения продавца. Pending disposition не означает ноль потерь; saleable-restored stock не является списанным COGS | Текущий accounting commit flow остаётся отдельным. Экспериментальная экономика не вызывает commit и не изменяет учёт себестоимости |
| Платное хранение и прочие услуги | Period accrual fee breakdown + явно настроенная `authorized_storage_mapping`; для отдельных операций возможны item fees | Периодная сумма — не доказанная SKU-сумма. Account-level хранение нельзя делить по выручке/заказам без выбранной allocation policy. Отсутствующая строка/тип не доказывает ноль | Period profitability completeness / experimental store report. Новая unit модель может показывать окно-распределение отдельно от exact SKU/cohort факта; остаток начислений не считать ещё одним расходом поверх детализации |
| Кросс-докинг | `CrossDockingUnitRateSource`: финансовые leaf accruals и принятые акты/количества; окно 56 завершённых local days `Europe/Moscow` | Строгая полнота страниц и type dictionary; SKU fee attribution + принятые fact quantities по тому же SKU. Знаменатель — поставленные cross-dock units, не продажи. Signed corrections остаются в сумме. Store shared fee не назначается SKU без доказанной политики | Существующий scenario source добавляет `cross_docking_per_unit` только при `evidence_complete` и `applicable_to_sku`. Это фактическая средняя на поставленную единицу, не себестоимость на проданную единицу и не exact expense конкретной будущей продажи |
| Экспериментальное наблюдение | `UnitPriceObservationCollectionService`: finance by accrual date, Performance by report date, FBO posting status + Returns changes в выбранном окне, owner-confirmed price/effective time | Окно локальных завершённых дней 3–56; FBO only; единая операция ограничена общим trace. Нет истории цены продавца на уровне каждой продажи; ручная подтверждённая цена — предположение владельца. Finance, CPC и FBO quantities имеют разные date bases | Нормализатор, quality, result, ranking и Telegram observation UI; результат остаётся `INSUFFICIENT_DATA`/modelled, пока цена, quantity, tax, COGS и spend не сопоставимы. Нельзя делать причинное утверждение об эффекте цены |
| Сохранение планов и наблюдений | Tenant SQLite `PlanningWorkspaceRepository`, DB schema version 5; documents, tariff profiles, observations, immutable observation results and comparisons | Существуют owner/store-scoped revisions, idempotency, CAS, limits and allowlists. Expense snapshot ledger и experiment baseline/candidate states отсутствуют | Расширять существующий repository additive migration и backup/restore. Не вводить вторую БД/expense repository |

## Публичный путь и переиспользование

- Главное меню → `unit_economics` → SKU → `TelegramUnitPriceCalculatorRuntimeService` → `UnitPriceScenarioSource` → `UnitPriceScenarioService`.
- Текущие вспомогательные пути: manual tariff profile, target-margin/ad-cap/grid/sensitivity, batch/mix, saved planning document, read-only observation `upo:*`, comparison/history/export. Их точные callback handlers собраны в `AssistantButtonHandlerService`; их должен сохранить будущий experiment flow.
- Периодный финансовый путь: `PeriodProfitQueryService` запрашивает daily summary, return evidence, mapped advertising/storage evidence, COGS coverage and completeness; это отдельный period report, не текущий one-sale calculation.
- Основные существующие регрессии источников: `tests/test_unit_price_scenario_source.py`, `tests/test_unit_price_scenario_service.py`, `tests/test_returns_buyout_facts_source.py`, `tests/test_returns_buyout_analytics_service.py`, `tests/test_returns_finance_attribution_facts_source.py`, `tests/test_returns_finance_attribution_analytics_service.py`, `tests/test_unit_price_observation_collection_service.py`, `tests/test_cross_docking_financial_evidence_service.py`, `tests/test_cross_docking_supply_evidence_service.py`, `tests/test_planning_workspace_repository.py`, `tests/test_telegram_unit_price_observation_runtime.py`.
