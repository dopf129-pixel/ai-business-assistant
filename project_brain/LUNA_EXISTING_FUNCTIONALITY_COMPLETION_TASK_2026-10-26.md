## 1. Результат задания

Довести существующие функции до состояния, когда:

1. Для каждого доступного действия известны вход, результат, источник данных, ограничения и проверенный путь пользователя.
2. Подтверждённые ошибки расчёта, отображения, сохранения и навигации исправлены.
3. Отчёт, его подробности, сохранённый план и экспорт согласованы по суммам, периоду, магазину и полноте.
4. Пользователь может получить необходимые сведения для сверки через существующие экраны и экспорты бота.
5. Данные сохраняются при повторном открытии и восстановлении; обновление и управление экземпляром проверены в изоляции.
6. Готовы небольшие PR с зелёным CI актуальных ревизий и пакетом для независимого review.

Не обещать «100% готовности» по количеству закрытых этапов. Отдельно показать техническую готовность, ограничения Ozon и незавершённую проверку владельцем.

Если сценарий уже реализован корректно и покрыт подходящей проверкой, закрыть его как VERIFIED_EXISTING со ссылкой на доказательство. Не переписывать рабочий код и не создавать новый тест ради отметки этапа.

## 3. Обязательные границы

### Сохранить действующие правила

- Финансовая прибыль строится существующим canonical pipeline. Не создавать второй финансовый движок и не восстанавливать фактическую комиссию как цену, умноженную на процент.
- Действующая политика налога остаётся в TaxService активного магазина. Использованная в августовском примере база «выручка минус баллы» — закреплённое правило проекта для соответствующей политики, а не новое налоговое решение этого ТЗ.
- Себестоимость действует с подтверждённой даты. Применение ко всей истории требует отдельного явного подтверждения.
- Return COGS не восстанавливается автоматически по возврату выручки или статусу Ozon. Сохранить inventory → attribution → recognition → authorization → explicit commit → final application.
- Сохранять owner/store/SKU isolation, TTL, immutable snapshots, CAS и совместимость saved plans v1/v2.
- Цена сценария — цена продавца. Калькулятор планирует одну успешную продажу FBO; FBS и прогноз спроса не добавлять.
- Кросс-докинг: 56 завершённых дней, signed начисления с корректировками, фактически поставленные и подтверждённые единицы; продажи не заменяют знаменатель.
- Подтверждённый ноль, отсутствующее значение, неполный источник и несовместимый показатель — разные состояния.
- Существующие разрешённые локальные записи стоимости, расхода и версии плана сохраняют preview/confirmation. Рекомендация не становится автоматически исполненным действием.

### Границы разработки

- Сначала читать AGENTS.md, CURRENT_STATE.md, DECISIONS.md, TEST_MAP.md и относящиеся к этапу документы.
- Не менять пользовательские JSON/SQLite, .env, ключи, локальные backups, lock-файлы или ACL. Не включать их в Git.
- Не запускать реального бота, не останавливать рабочий экземпляр, не выполнять реальное обновление, backup/restore пользовательских данных или live Ozon/Telegram requests.
- Не выполнять merge/deploy. Конечный технический результат — PR и review handoff.
- Не вводить автоматическое изменение цен, рекламных кампаний, карточек и поставок Ozon.
- Не добавлять новую систему уведомлений, прогнозирования, новый UI, новый финансовый pipeline или неподтверждённые API вместо завершения текущих путей.
- Не делать массовый рефакторинг, переименование всей архитектуры и миграцию всей документации.
- Не требовать платную подписку Ozon для приёмки поддерживаемых сценариев. Недоступный источник честно остаётся ограничением.
- Raw API, исходные отчёты владельца, Client ID, SKU, номера отправлений/поставок, токены и ключи не публиковать в Git, CI и PR.

Рутинные решения Luna принимает самостоятельно. Новое финансовое правило, новый способ распределения общих расходов, ослабление подтверждения записей или новый продуктовый функционал требуют решения владельца.

## 4. Что считать незавершённостью

Каждую находку классифицировать до изменения кода:

| Класс | Пример | Действие |
|---|---|---|
| CONFIRMED_DEFECT | При учтённом кросс-докинге экран утверждает, что он исключён | Воспроизвести, исправить, добавить необходимую регрессию |
| WORKFLOW_GAP | У существующего результата нет достижимого обещанного перехода | Довести текущий путь, не создавать параллельный модуль |
| VERIFIED_EXISTING | Сохранённый план открывается без Ozon и сохраняет исходную версию | Сослаться на подходящую успешную проверку |
| SOURCE_LIMITATION | Analytics не возвращает cancellations | Сохранить неизвестность, объяснить источник и допустимое действие |
| OWNER_EVIDENCE_PENDING | Нет JSON текущего работающего бота для сверки | Подготовить один пакет получения данных и продолжить независимые этапы |
| OUT_OF_SCOPE_PRODUCT | FBS-планирование или прогноз спроса | Записать кратко для будущего обсуждения; не реализовывать |

Не считать старую запись «PR открыт», название TODO или исторический failed test доказательством текущего дефекта. Проверять актуальный код, SHA и последующее исправление.

## Модуль C. Кросс-докинг

### Z07 — проверяемое 56-дневное evidence

### Z08 — несколько SKU, корректировки и неполные поставки

1. Проверить отдельные расходы SKU и общие расходы магазина, отсутствие смешения tenant/window/model.
2. Signed корректировки включаются один раз; повторные/конфликтные записи не удваивают сумму.
3. Знаменатель основан на принятом фактическом количестве по подтверждённой семантике акта. declared, approved и fact не складываются.
4. Сохранить существующее консервативное правило дат для завершённой заявки с одной подходящей вложенной поставкой. created_date акта и deprecated arrival_date не становятся датой приёмки без доказательства.
5. Проверить partial/split/многотоварную поставку, unknown SKU, полное окно без поставок SKU, положительные начисления-корректировки и отрицательный net expense.
6. Фраза владельца «1 поставка = 1 товар» описывает его текущую практику; не превращать её в универсальный контракт Ozon.

Приёмка: неполные/неоднозначные поставки не дают ложный точный тариф; store estimate подписана оценкой магазина, не выдана за индивидуальный расход SKU.

### Z09 — единичное включение и сохранённая версия

1. Проследить ставку в текущей unit economics, single, target price, batch, sales mix, readiness, comparison и export.
2. Компонент вычитается ровно один раз с сохранением существующей налоговой политики.
3. В плане объёма ставка умножается на заданные успешные продажи Q; это плановое допущение, не факт новых поставок.
4. v1 сохраняет старую формулу. v2 использует замороженное evidence; открытие не обновляет его, explicit refresh создаёт новую revision/copy.
5. Отсутствие ставки и полная выборка без подходящих единиц остаются различимы. Сохранить действующее различие между оценкой single без компонента и неполным итогом mix с положительным Q.

Приёмка: одна ставка проходит весь путь без изменения значения/смысла и без повторного Ozon read при просмотре; фактическая сторона plan/fact не получает плановое вычитание.

## Модуль D. Калькулятор и планы

### Z10 — согласованность результата и текста калькулятора

Конкретная найденная точка: TelegramUnitPriceCalculatorRuntimeService._price_planning_result_screen выводит фиксированный текст «Общие расходы, хранение, кросс-докинг и возвраты не включены», тогда как существующий target solver сохраняет cross_docking_per_unit и forward result учитывает его.

1. Воспроизвести через публичный сценарий целевой маржи и сравнения цен с подтверждённой ставкой.
2. Исправить подпись по фактическому forward result/evidence: включённый компонент, неизвестный компонент и legacy v1 имеют разные сообщения.
3. Пройти основной результат, допущения, target result, comparison, sensitivity, рекламный предел и saved view; исключить противоречащие друг другу предупреждения.
4. Добавить регрессию поведения public flow, где числовой результат и подпись проверяются вместе. Не ограничиваться тестом поиска одной строки в файле.

Приёмка: пользователь видит, какие компоненты реально включены в показанный результат. Изменение подписи не меняет финансовую формулу.

### Z11 — целевая маржа, цены и допустимая реклама

1. Проверить zero-profit/target solver через тот же forward calculator, включая неизменную историческую ставку кросс-докинга.
2. Границы цены, шаг копейки, Decimal parsing, округление и максимум вычислений должны быть проверяемы; недостижимая цель имеет отдельный результат.
3. Для рекламного предела проверить повторную forward-проверку предложенного значения и существующие налоговые режимы/минимальный налог.
4. Обновление источников и применение выбранного значения сохраняют остальные ручные допущения только при совпадении identity.
5. FBS, будущие скидки и будущий тариф не объявлять известными. Среднее баллов остаётся измеренным взвешенным допущением с окном и coverage.

Приёмка: заявленная достижимая цена/реклама подтверждается forward result; input parser не теряет копейки; применение не меняет цену Ozon.

### Z12 — жизненный цикл сохранённого плана

1. Пройти create → list → open → continue local → preview → save revision/copy → reopen.
2. Проверить существующие metadata actions, optimistic version/CAS и случай двух подтверждений/двух открытых карточек.
3. После перезапуска читается прежний снимок с теми же assumptions/model; без автоматического refresh или миграции чисел.
4. Проверить другой owner/store, смену SKU/product/offer identity и устаревшие action tokens.
5. Отдельно подтвердить, что исправление локального черновика не переписывает историческую revision.

Приёмка: сохранённые планы воспроизводимы; конфликт не теряет новую запись и не заменяет другой товар; старые схемы читаются как прежде.

### Z13 — batch, mix, готовность, сравнения и экспорт

1. Связать одиночный калькулятор с batch и saved mix для трёх разных SKU.
2. Проверить неизвестное Q против явного нуля, отсутствующую себестоимость, неподтверждённый кросс-докинг и подтверждённый пустой список внешних расходов.
3. Mix использует текущую политику округления компонентов и один общий TaxService расчёт, не сумму независимо округлённых налогов SKU.
4. Readiness ведёт к конкретному отсутствующему входу; после изменения новый результат/версия не смешивается со старой карточкой.
5. Plan/fact сравнивает только доказанно совместимые величины за одинаковый период и exact SKU. Не включать сравнение общей прибыли, если scopes рекламы/расходов/Return COGS не совпадают.
6. CSV/JSON экспортирует весь открытый снимок, model version, assumptions и coverage, а не только видимую страницу.

Приёмка: subtotal не называется полным итогом; историческое сравнение не запрашивает Ozon; экспорт соответствует показанному варианту.

## Модуль E. Пользовательские пути

### Z14 — достижимость всех существующих действий

1. Пройти реестр Z01 от /start через выбор магазина и главные кнопки до результата/возврата.
2. Проверить пустой каталог, неизвестный SKU, неоднозначный offer, неподключённый магазин и отсутствие обязательных настроек.
3. Проверить переходы обзор → решение → калькулятор → сохранённый план; report → completeness → стоимость/расход → исходный report → refresh.
4. Для legacy анализа, плана действий, истории и памяти проверить существующие правила доступа и scope. Не включать новые автоматические действия для «завершения» раздела.
5. Удалять/скрывать рабочую пользовательскую функцию не решать самостоятельно. Неисправимый без нового бизнес-правила legacy gap вынести владельцу с конкретным сценарием.

Приёмка: видимая кнопка имеет рабочий handler; помощь соответствует реальным названиям; у поддерживаемого сценария есть выход/возврат без потери правильного контекста.

### Z15 — старые кнопки, параллельные операции и источники

1. Проверить смену магазина/пользователя/периода/SKU между началом запроса и ответом.
2. Старый callback не читает чужой snapshot и не подтверждает новый draft; поздний результат не показывается в новом магазине.
3. Duplicate request/confirm, TTL expiry, cache eviction и concurrent read должны завершаться контролируемо без KeyError и повторной записи.
4. Ozon Seller и Performance используют общий physical HTTP/time budget родительской операции; retry и ожидание входят в него.
5. После ошибки дедупликация/lock очищаются; новый явный запрос возможен. Просмотр, сортировка и export готового снимка не увеличивают source query count.

Приёмка: источниковая работа ограничена измеряемыми счётчиками, устаревшие данные не подменяют новый контекст, повтор не приводит к двойной записи.

### Z16 — понятные отчёты и доставка сообщений

1. Согласовать русский текст, термины, разделители тысяч, копейки, знак и проценты на главных существующих экранах.
2. Рубли делить на подтверждённую выручку; штуки — только на совместимую базу количества. При нулевой/неположительной базе не показывать выдуманный процент.
3. Основной экран короткий; сведения источника/ограничений достижимы в подробностях. Не терять предупреждения при сокращении.
4. Длинные ответы и emoji проходят UTF-16-aware splitter; клавиатура на последнем сообщении; ошибка отправки не превращается в успешный save.
5. Поддержка получает только allowlisted diagnostic JSON. Финансовый owner export с суммами — другой формат; не ослаблять support redaction.

Приёмка: данные не обрезаны лимитом Telegram, статус понятен без чтения raw кодов, вывод не противоречит фактическим включённым расходам.

## Модуль F. Эксплуатация

### Z17 — обновление существующей установки и инструкции

1. Проверить пути новой и уже существующей установки по текущим scripts, не запуская их на рабочем экземпляре.
2. Особо описать первый переход со старого checkout, где ещё отсутствует update_bot.ps1, и случай dirty tracked/untracked документа.
3. Инструкция не должна предлагать git restore/reset/clean или удаление файла как универсальное исправление. Сначала определить владельца изменения и сохранить нужную копию вне incoming tracked пути.
4. После появления штатного updater использовать его действующие CheckOnly/NoStart/normal contracts и verified backup boundary.
5. Любые команды для владельца давать по одной законченной копируемой команде на блок; многострочный PowerShell оформлять целым блоком с настоящими переводами строк.

Приёмка: памятка выполнима из чистого PowerShell без скрытой зависимости от ранее выставленного PYTHONPATH; не смешивает старую и новую версии entrypoints.

### Z18 — backup/restore с реальными форматами хранилищ

1. На synthetic данных пройти supported storage inventory → backup → verify → dry-run → новый root → чтение всеми нужными repositories.
2. Проверить tenant stores, legacy JSON list/dict форматы, планы/revisions, стоимость/effective dates, расходы/coverage и mapping registry.
3. В synthetic SQLite создать зашифрованную Ozon credential запись. В архиве допустимы Client ID и ciphertext; plaintext API key, Telegram token и master key исключены.
4. Восстановление с тем же отдельно переданным synthetic master key читает запись; отсутствие/другой ключ даёт безопасную ошибку, не пустой «успешный» магазин.
5. Сохранить limits, checksums, timeout SQLite, path traversal/symlink guards, новый root и неизменность исходного storage при ошибке.

Приёмка: восстановленный поддерживаемый state читается без потери scope/версии; исходные данные не затронуты; инструкция точно описывает содержимое архива.

### Z19 — управление экземпляром и сбои обновления

1. Synthetic lifecycle показывает polling readiness отдельно от наличия PID и валидности локальной конфигурации.
2. Stop связан с checkout и исходным поколением процесса; другой экземпляр не завершается.
3. Update проверяет canonical remote/main, immutable SHA, dirty/untracked/ignored пересечения и не использует force overwrite.
4. Общий startup/maintenance guard удерживается на всём окне; проверить конкурентный start/update/backup.
5. Пройти сбои stop, backup, dependency installation, fast-forward, healthcheck и readiness. Вывод точно сообщает состояние и безопасное следующее действие, не запускает скрытый rollback/restore.

Приёмка: controlled failures не теряют данные, не оставляют ложный RUNNING и не требуют убийства произвольного Python.

### Z20 — воспроизводимая изолированная проверка

Выполнить после Z00–Z02 до файловых тестов остальных модулей.

1. Установить подтверждённые dev dependencies в предназначенное для проверок окружение.
2. Отключить dotenv и live credentials. До создания factory/repositories задать отдельные synthetic storage/temp; проверить legacy project-root paths, которые не перенаправляются одной env-переменной.
3. Не повторять известный полный Windows pytest в папке с ACL-ограничениями. Использовать чистое доступное окружение; если ограничение повторилось — зафиксировать infrastructure failure и выполнить стандартный полный профиль в GitHub CI.
4. Не менять ACL, не удалять чужие temp, не переписывать assertions под ошибочный результат и не скрывать регрессии через общий skip.
5. После каждого изменения запускать нужный профиль; полный набор — на финальном коде и в штатном CI. Повторять уже зелёную полную проверку только при новом изменении/ошибке/обоснованном риске.

Приёмка: команды и результаты воспроизводимы, tests и app/tests учтены; локальный deselected не заявлен пройденным; пользовательские data paths не изменились.

## Модуль G. Приёмка и передача

### Z21 — сквозная техническая приёмка

Повторно использовать уже существующие связные тесты; добавлять только недостающие проверки поведения.

Обязательные цепочки:

Приёмка: все подтверждённые P1/P2 в scope закрыты; полный штатный pytest и compile зелёные на финальной ревизии Windows/Python 3.12 и Linux/Python 3.11; Linux production Docker build/runtime smoke успешны.

### Z22 — небольшие PR и независимый review

1. Коммиты группировать по одному подтверждённому дефекту/связанному пользовательскому пути: исправление + нужная регрессия + документация.
2. Не создавать один огромный commit «всё завершено» и новые сервисы лишь для формального выполнения этапов.
3. При зависимых PR явно указать порядок и base/head; закрытая техническая база нового пакета — актуальный main, не старый открытый stack #712–#717.
4. PR description описывает окончательное поведение, известные ограничения и проверки именно текущего SHA.
5. Подготовить review map: расчёты, scope, CAS, сохранность storage, совместимость, budget, exports, влияние на архитектуру.
6. Собственный self-review не выдавать за независимый approval. Не выполнять merge или deployment.

Приёмка: PR опубликованы, CI актуальных heads зелёный, неснятых подтверждённых P1/P2 нет, review handoff содержит точные ссылки и оставшиеся внешние вопросы.

### Z23 — один пакет проверки владельцем и итоговый статус

1. Подготовить короткую инструкцию с точными существующими кнопками: версия процесса → расчёт закрытого периода → owner JSON → нужные aggregate сведения кросс-докинга.
2. Суммы/периоды сохранить для сверки; идентификаторы маскировать локально стабильными псевдонимами. Не просить .env, Client ID, API keys, master key, полную БД или raw logs.
3. Если нужный материал уже получен в рамках исполнения, использовать его. Не просить повторно и не называть старое сообщение текущим runtime result.
4. Для августа сопоставить только одинаковые period/scope/date basis. Второй период и реальная multi-SKU проверка желательны, но их отсутствие не подменять фиктивным evidence.
5. Отдельно оставить реальную проверку 56-дневного знаменателя и 24–72 часа работы. Synthetic soak это не заменяет.
6. Не останавливать всю программу ради ожидания этих материалов. Сдать техническую часть и единую таблицу OWNER_EVIDENCE_PENDING.

Итоговые допустимые состояния:

- ENGINEERING_READY_OWNER_PENDING — код, CI и документация готовы, внешний evidence перечислен;
- ENGINEERING_READY_SOURCE_LIMITED — поддерживаемые сценарии проверены, доказанные ограничения источников явно видимы;
- OWNER_ACCEPTED — только после фактически полученной и сопоставленной проверки владельцем;
- BLOCKED — конкретный нерешаемый блокер с выполненными попытками и минимальным вопросом.

Приёмка: итог не утверждает «весь функционал завершён в production», если реальная проверка не проведена.

Статусы этапов: NOT_STARTED, IN_PROGRESS, VERIFIED_EXISTING, IMPLEMENTED, VERIFIED, BLOCKED. OWNER_EVIDENCE_PENDING ведётся отдельным полем и не повышает технический статус.

Обновлять:

- текущий progress — после каждого этапа;
- CURRENT_STATE — по завершённому модулю, без ложного production acceptance;
- TEST_MAP — только для новых/изменённых тестовых контрактов;
- CHANGELOG — для пользовательских изменений;
- DECISIONS — только для нового/изменённого архитектурного решения;
- README/user guide/runbook — если изменился соответствующий пользовательский путь.

Не размножать acceptance-файлы на каждую тривиальную операцию. Достаточно одного проверяемого реестра функций, findings и evidence с понятными ссылками.

## 9. Автономность и остановки

- Работать по доступным зависимостям без запроса подтверждения каждого этапа.
- После сокращения контекста читать task, последнюю запись progress, git status/diff и фактический head. Продолжать незавершённый этап.
- Не запускать повторы ради времени работы и не откладывать готовую передачу до условных восьми часов.
- Недоступный отчёт/владельческое наблюдение записать один раз и продолжить независимую часть.
- Обратиться к владельцу только при необходимом бизнес-решении или блокере, который нельзя решить доступными средствами. Вопрос должен содержать конкретный сценарий, выполненные попытки и варианты.
- Завершить на reviewable PR с зелёным CI и честно указанной внешней приёмкой. Слияние, развёртывание и запуск рабочего бота выполняются отдельным поручением.
