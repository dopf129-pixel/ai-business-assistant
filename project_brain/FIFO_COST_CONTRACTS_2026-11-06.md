# FIFO cost history contracts

Date: 2026-11-06  
Status: implementation contract for FC04–FC35; factual inventory cutoff remains source-blocked per FC02.  
Specification: `LUNA_FIFO_COST_HISTORY_TASK_2026-11-06.md`  
Architecture proposal: `DECISIONS_066.md`

## 1. Scope and authority

This contract defines a simplified FIFO cost pool for one exact seller SKU in one Ozon store. It allocates confirmed cost to confirmed units; it does not prove which physical batch Ozon picked and is not a home WMS. Factual Period Profit may consume a FIFO allocation only when the inventory anchor, sale event identity, and cutoff bridge are all reconciled. Current FC02 evidence does not meet that gate, so the integration status remains unavailable until owner validation proves the needed source semantics.

The new `FifoCostRepository` owns factual FIFO events and their projections. It uses the existing tenant-local `ozon_assistant.db` path through `tenant_storage`; it does not create a second database. `PlanningWorkspaceRepository` continues to own only plans, observations, and experiments. Planning Workspace's database migration version is stored in its own `planning_schema` table; FIFO migrations use a separate `fifo_cost_schema` table and an atomic transaction. Neither migration changes SQLite's independent `PRAGMA user_version`. FC06 creates `fifo_cost_streams`, `fifo_cost_sources`, `fifo_cost_source_refs`, `fifo_cost_policy_revisions`, `fifo_cost_events`, `fifo_cost_layers`, `fifo_cost_projections`, `fifo_cost_allocations`, `fifo_cost_allocation_lines`, and `fifo_cost_idempotency` alongside the FIFO schema metadata. FC07 schema v2 adds append-only `fifo_cost_commands` and `fifo_cost_command_events` and migrates v1 atomically. FC16 schema v6 adds an allocation header's captured `stream_revision` and append-only `fifo_cost_allocation_rate_lines`; FC18 v7 adds exact prior allocation basis for saleable returns; FC19 v8 adds separate append-only estimated non-sale outflow valuation lines; FC20 v9 adds append-only `fifo_cost_late_entry_drafts`, which stores owner-entered late-transition data and redacted accepted-supply evidence pinned to the expected stream revision; FC22 v10 adds append-only `fifo_cost_late_entry_corrections` containing the correction's exact draft/rate link, stream/allocation/source/tax revisions, period fingerprints, impact snapshot, and idempotency key. Corrections are inserted atomically with the rate change; prior drafts, rates, and allocation snapshots are not updated. A confirmed correction invalidates the active allocation projection until a complete replay is published, so it does not retroactively alter Period Profit by itself. Older allocation headers receive `stream_revision=0` and are stale until replayed. Preview tickets are held in memory, scoped to the current owner, replaced by a newer draft, expire after ten minutes and are invalid after restart; only the normalized confirmed command enters SQLite. The existing backup captures the whole SQLite file, so no separate file-list registration is needed; FC31 still verifies restore behavior.

The repository is additive. Existing `product_costs`, `product_cost_history`, `product_cost_switch_history`, finance authority, `TaxService`, forward calculator, Return COGS authorization/recognition, and saved-plan schemas retain their owners and existing meaning. No legacy costs are automatically converted into inventory layers. FC18 schema v7 adds append-only `fifo_cost_return_basis`, pinning each accepted restock to its prior allocation revision and original sale allocation line(s); FC19 schema v8 adds append-only non-sale outflow valuation lines separately from sale COGS; FC20 schema v9 adds only a late-entry draft and does not itself create a receipt event/layer or change FIFO quantity/rate projection; FC22 schema v10 adds an append-only preview/correction record and requires a subsequent allocation replay before the corrected cost becomes the active Period Profit basis; FC23 schema v11 adds an append-only cancellation record for an unused future rate. FL21 now replays only exactly linked, already validated saleable returns and supported non-sale outflows. Returns restore their original saved FIFO basis; outflows remain separate from sold units and sales COGS. Unknown or unlinked movements still block. Neither behavior modifies or replaces Return COGS records.

## FC22 late-entry correction contract

`FifoCostLateEntryImpactService` reports before/after units and COGS by existing FIFO basis, then calculates period tax/profit through the current `TaxService`. Physical sale dates order FIFO events; exact sale-identity digests from complete finance summaries assign COGS to financial recognition periods. The mapping must be one-to-one and cover every replayed sale, and its fingerprint is bound into preview/confirmation. Complete before/after summaries must cover the full dependent sale horizon and carry valid money/source fingerprints; replay must preserve exact sale identity and quantity on both sides. When the before allocation or a complete baseline is unavailable, the result may expose candidate COGS only and must not expose tax, profit, or deltas. Missing or stale financial mapping cannot produce an impact. `FifoCostLateEntryCorrectionService` binds confirmation to exact owner/store/SKU/draft and the impact fingerprint; the repository rechecks stream, allocation, source, financial-period mapping and preview revisions in the same SQLite transaction that appends the new rate and correction. Corrections leave Period Profit unchanged until replay; the projection is explicitly marked incomplete. Only one previously missing rate and histories without unsupported rate transitions are supported; a late correction against existing active multi-rate history still returns `FIFO_REPLAY_RATE_TRANSITION_UNSUPPORTED`. The unresolved historical inventory/finance cutoff continues to block real seller data.

## FC23 rate boundaries and cancellation

FIFO schema v11 adds append-only `fifo_cost_rate_cancellations`. It records cancellation of the latest unused future rate without editing/deleting the original rate, retains sequence history, and exposes cancellation status without raw IDs. Preview and commit are bound to exact owner/store/SKU, stream revision, source fingerprint, expiry and idempotency key. A rate cannot be cancelled after a sale/movement on or after its boundary, allocation against the rate, or a reconciliation for that transition. Cancelling the final unused rate permits a later rate to receive a new monotonically increasing sequence.

Date-only rates must be strictly later than the previous active rate and latest finite layer; equal dates do not imply an intra-day order. Rate reconciliation snapshots must be complete, exact-SKU and dated for the transition, and cannot be future-dated relative to the request's clock (`FIFO_RATE_RECONCILIATION_FUTURE_SNAPSHOT`). Cancelled rates are excluded from current projection and replay selection. Unsupported multi-rate late reconstruction and unproven production cutoff remain fail-closed gaps. Return/non-sale movement behavior is extended by the FR10 contract below.

The Telegram SKU history shows a cancellation action only while a future rate is planned. It previews cancellation, confirms with the existing opaque user/store/revision-bound ticket, and refreshes the history view after a successful append. If the stream changes between preview and confirmation, the stale callback fails without writing. The UI targets the newest planned rate because the repository permits cancelling only the latest unused rate. Callback data contains only the action and short-lived opaque ticket; preview IDs and idempotency keys stay server-side.

## 2. Identity and tenancy

Every stream is scoped by the current tenant (the tenant-local database) and exact `store_id`. The normalized product identity contains `product_id`, `offer_id`, and Ozon `sku`; at least one stable product identifier plus SKU must be present. A stream key is derived from a canonical serialization of `(store_id, product_id, offer_id, sku, cost_policy_version)`. Missing or ambiguous store/product mapping is an error, never a global or cross-store fallback.

If the seller changes an offer/SKU mapping, the repository requires an explicit identity-link event backed by an already-supported catalog identity mapping. It does not merge old/new identities by display name. One supply may contain one SKU and multiple same-SKU cost layers only when their quantities and costs are explicitly split and reconcile to accepted quantity.

## 3. Money, quantity, and time

- Currency is RUB in this release. New user amounts are parsed as `Decimal`, finite and non-negative, then normalized to canonical two-decimal strings with the project's established half-up rounding at the input boundary. Never persist new FIFO money as SQLite `REAL` or perform arithmetic through `float`.
- A unit cost is the all-in purchase cost for one sellable SKU unit: purchase, delivery to the owner, and packaging. If components are supplied, the canonical unit amount must equal their exact normalized sum. Ozon commission, logistics, advertising, tax, storage and cross-docking remain separate model components and are never folded into acquisition cost again.
- Quantities are positive integers for layer additions and sale/acceptance quantities; confirmed zero is a separate accepted observation, never a missing value. Boolean, fractional, negative, non-finite, overflow, or mismatched quantities are invalid. Initial implementation caps: 100,000 units per event, 1,000,000 units in one active stream projection, 64 KiB normalized event, 100,000 replayed events per synchronous replay segment. Exceeding replay work returns a bounded continuation/incomplete result and never a partial factual result.
- Persist exact UTC `effective_at` only when source precision supports it. Also retain `effective_date`/store timezone, `recorded_at`, `captured_at`, `source_as_of`, `inventory_cutoff`, and finance `accrual_date` as distinct fields. Date-only evidence never becomes an invented midnight timestamp. If same-day ordering changes FIFO allocation and cannot be proven, return `EVENT_ORDER_UNRESOLVED` and require a correction/owner confirmation or keep the period unavailable.
- Local response receipt time is collector `captured_at`; it is not an Ozon server snapshot time. Finance recognition date is not silently renamed physical sale time.

## 4. Evidence envelope

Every normalized source fact has an allowlisted envelope:

`schema_version`, `source_kind`, `source_method`, `source_status`, `scope`, `identity`, `quantity`, `unit_cost_rub`, `currency`, `effective_at`, `effective_date`, `recorded_at`, `captured_at`, `source_as_of`, `inventory_cutoff`, `coverage`, `completeness`, `provenance`, `source_fingerprint`, `supersedes_event_id`, `reason_code`.

Allowed provenance values: `OWNER_CONFIRMED`, `OZON_CONFIRMED_FIELD`, `DOCUMENT_RECONCILED`, `LEGACY_DATED_COST`, `MODEL_ASSUMPTION`. Values are not interchangeable. `MODEL_ASSUMPTION` cannot enter factual cost allocation or Period Profit. `OWNER_CONFIRMED` preserves what the seller stated; it is not labeled an Ozon fact.

Never persist raw Seller API responses, credentials, Client ID/API key, Telegram callback tokens, product titles, barcodes, or raw posting/supply/act identifiers. Persist only the minimum normalized values required for replay and a source identity digest for deduplication. Diagnostics show field names/status/counts and sanitized issue codes only.

## 5. Event and state contracts

Event kind allowlist for the first release:

- `OPENING_FIFO_ANCHOR`: per-cost quantity layers at an owner-confirmed cutoff, with disjoint Ozon / old goods in transit / old-at-home counts and source provenance.
- `COST_LAYER_RECEIPT`: quantity of one cost basis accepted into the FIFO pool. A purchase document alone can confirm cost but does not assert that the whole purchased quantity is available to sell. A new layer's quantity is only the portion explicitly reconciled to a received/accepted quantity or separately owner-confirmed inventory.
- `INVENTORY_TRANSFER`: movement between home, transit and Ozon of units already counted in the pool. It changes location evidence, not total FIFO quantity; it must not create the same units a second time.
- `PHYSICAL_SALE`: exact posting+SKU quantity with a proven cutoff/event ordering. Finance accrual is a monetary recognition link, not a second sale event.
- `SALE_CANCELLATION`: cancel a prior sale only when the underlying source proves no physical sale occurred; it does not retroactively delete the event.
- `SALEABLE_RETURN_RESTOCK`: explicit eligible, saleable inventory restoration linked to its original sale and matching quantity. Existing Return COGS recognition/authorization gates still apply independently.
- `NON_SALE_OUTFLOW`: an explicit loss, damage, write-off, or other non-sale removal with a supported reason and quantity.
- `CORRECTION`: immutable replacement event with `supersedes_event_id`, reason and impact preview; no UPDATE/DELETE of prior events.

Stream state is `LEGACY`, `FIFO_PENDING_ANCHOR`, `FIFO_READY`, `FIFO_PARTIAL`, `FIFO_CONFLICT`, or `FIFO_SOURCE_BLOCKED`. Source completeness is a separate status: `COMPLETE`, `PARTIAL`, `UNAVAILABLE`, `STALE`, `CONFLICT`, `NOT_REQUESTED`, `OWNER_CONFIRMED`, or `MODEL_ONLY`. `FIFO_READY` requires a verified anchor, event continuity, exact identity, no unallocated movement, a matching revision and successful reconciliation. A numeric total by itself is never a readiness status. `FIFO_READY` means the owner-confirmed opening queue is coherent for the recorded scope; it does not mean Period Profit's physical-sale/cutoff bridge is proven.

The explicit error/reason allowlist includes `HISTORY_GAP`, `ANCHOR_UNCONFIRMED`, `INVENTORY_CUTOFF_UNRECONCILED`, `PHYSICAL_SALE_IDENTITY_UNCONFIRMED`, `STOCK_SEMANTICS_UNCONFIRMED`, `TRANSIT_OVERLAP_UNRESOLVED`, `SUPPLY_COST_LINK_MISSING`, `EVENT_ORDER_UNRESOLVED`, `RECONCILIATION_CONFLICT`, `STALE_PREVIEW`, `REVISION_CONFLICT`, `BUDGET_EXHAUSTED`, `SOURCE_UNAVAILABLE`, and `PERIOD_PROFIT_COST_LEGACY_PROVENANCE_AMBIGUOUS`. FC04's pure-kernel results additionally use `FIFO_SOURCE_INCOMPLETE`, `FIFO_LAYER_INPUT_INVALID`, `FIFO_LAYER_INPUT_LIMIT`, `FIFO_OPEN_RATE_INPUT_INVALID`, `FIFO_LAYER_ID_DUPLICATE`, `FIFO_EVENT_INPUT_INVALID`, `FIFO_EVENT_ID_DUPLICATE`, `FIFO_STREAM_QUANTITY_LIMIT`, `FIFO_ANCHOR_LAYER_MISSING`, `FIFO_ZERO_ANCHOR_HAS_LAYERS`, `FIFO_CONFIRMED_QUANTITY_EXHAUSTED`, `FIFO_RETURN_BASIS_MISSING`, `FIFO_RETURN_BASIS_QUANTITY_MISMATCH`, `FIFO_RETURN_ORIGIN_SALE_MISSING`, `FIFO_RETURN_ORIGIN_LAYER_MISSING`, `FIFO_RETURN_QUANTITY_EXCEEDS_ORIGIN`, `FIFO_RESTORED_LAYER_ID_CONFLICT`, `FIFO_CURRENCY_UNSUPPORTED`, `FIFO_EVENT_QUANTITY_LIMIT`, `FIFO_REPLAY_EVENT_LIMIT`, and `FIFO_REPLAY_WORK_LIMIT`. Any incomplete result has no published allocation or money total.

## FC12 history and owner rate-entry UI

`FifoCostHistoryService` reads one exact tenant/store/product/offer/SKU stream and exposes saved cost layers, rate components, provenance, date-only boundaries, and the last allocation summary without raw IDs or fingerprints. It reports remaining layer quantity and next-unit cost only at the confirmed anchor snapshot when no later movement is present; any movement that would require replay makes those quantities unknown and suppresses a current next-unit claim. A rate remains separate from finite stock and is labelled planned/effective as of the display date. The owner-reported old-home remainder is shown as reconciliation evidence and explicitly not as an additional current inventory quantity.

The existing seller-cost menu adds a separate FIFO-history button per visible exact SKU. History callbacks are random opaque tokens scoped to Telegram user and active tenant/store, bound to the stream revision, bounded to 1,024 process-local tickets and expire after 15 minutes. A callback after a store change, revision change, expiry or restart fails closed. “New cost” collects purchase, delivery to owner, packaging and an explicit old-home quantity through Decimal/integer parsing, shows a read-only preview, and confirms through the FC11 CAS/idempotency boundary. The confirmation draft is user/store scoped, bounded to 128 process-local drafts and expires after ten minutes. It records no new-batch quantity, leaves all finite old layers unchanged, and cannot make Period Profit factual while the cutoff is unreconciled. “Already sent” and “correct record” are explicit non-mutating placeholders until their dependent stages; neither writes through the legacy cost setter.

## FC13 linked supply/act evidence

FC13 upgrades FIFO schema v3→v4 with append-only `fifo_cost_supply_evidence`. A completed, exact-store/SKU read can be linked to the existing stream with separate opaque digests for `order_id`, `supply_id`, and each `act_id`; raw API identifiers and payloads are not persisted. Per accepted act, the normalized evidence keeps `declared_quantity`, `approved_quantity`, and `fact_quantity` separate. `fact_quantity` is the accepted unit count; `approved_quantity=0` is preserved as zero and is never treated as a zero acceptance when `fact_quantity` is positive. The summary's fact total must reconcile exactly to product lines for each accepted act and the selected supply must contain exactly the target SKU.

`created_date` is kept as `DOCUMENT_CREATED_DATE_ONLY`; `captured_at` describes local collection time. Per-stream `snapshot_sequence` orders append-only evidence revisions independently from stream revision. `source_as_of`, physical `effective_at`, and physical `effective_date` remain null. The source snapshot is evidence only: recording or refreshing an act does not create a `COST_LAYER_RECEIPT`, increase FIFO inventory, change the stream revision, or add the separately owner-reported old-at-home quantity. An identical source refresh is idempotent; changed act content appends a new evidence snapshot while preserving the earlier version. A missing/unavailable/partial source is not persisted as complete evidence.

## FC14 — repeated rates and finite-layer reconciliation

FC14 upgrades FIFO schema v4→v5 with append-only `fifo_cost_rate_reconciliations`. A later rate is previewable only with a complete, exact store/product/offer/SKU stock snapshot captured on its date boundary and an explicit owner confirmation of reconciliation scope. FBO `present` includes reserved units, so the reserved subset is stored for audit but never added to the total twice; only disjoint confirmed transit and owner-reported old-home units are added. The total first covers all confirmed older finite layers; the remainder is the previous open rate. Thus third/fourth rates do not rewrite earlier quantities or costs. A total below older layers is `FIFO_RATE_RECONCILIATION_CONFLICT`; a decrease from the prior complete total is `FIFO_RATE_STOCK_DISCREPANCY`, not an inferred sale. Any un-replayed inventory movement, incomplete/ambiguous source, or history gap blocks preview. Confirmation appends rate and reconciliation atomically with stream revision/sequence CAS and idempotency; old rows have update/delete guards. History exposes quantities and capture time, not source fingerprints.

The production source collector remains unable to produce an accepted complete reconciliation while FC02's v4 field semantics and common inventory/finance cutoff are unproven. FC14's repository/service path is verified with synthetic snapshots only; a Telegram owner-facing failure message keeps the new rate unsaved. This gate does not alter factual Period Profit or claim that recorded rates are physical receipts.

## FC15 — stable sale identity with a separate physical-time gate

`FifoCostSaleEvidenceNormalizer` computes a domain-separated `source_identity_digest` from the exact store, Ozon `posting_number`, and a confirmed stable seller `offer_id` (preferred) or `product_id`. The catalog SKU is validated as source evidence but is not part of the digest when the stable seller identity is confirmed, so a SKU rewrite does not create a second sale identity. Raw posting numbers, SKUs, product IDs, and offer IDs are not returned by the normalizer. Financial accrual dates are separately normalized/deduplicated and never promoted to `physical_effective_date`.

An event remains ineligible for FIFO unless the physical sale authority, physical-date semantics, and common inventory/finance cutoff bridge are all explicitly confirmed. Order/return status, monthly row count, and finance accrual date alone are not enough. The current normalizer is a pure boundary and is not wired to event storage; FC15 is `DONE_WITH_GAP` until a sanitized owner response confirms the actual realization row shape, sale-date coverage, and shared cutoff. Factual Period Profit remains untouched.

## 6. Anchor, layers, and FIFO allocation

An anchor is a frozen preview containing `(store, exact SKU identity, captured interval, old layers/cost provenance, FBO observation, transit not already present at Ozon, old home remainder, reserve treatment, exclusions, current stream revision, source fingerprints)`. The seller separately confirms old-at-home remainder; blank is not zero. The preview does not write. Commit rechecks owner/store/SKU, expected revision, captured source fingerprints, idempotency key and current cutoff state atomically.

FC10 adds `FifoCostAnchorService` for a manual owner-confirmed start. The owner supplies the date-only inventory cutoff and every existing cost layer in oldest-to-newest order. Each layer must explicitly contain non-negative integer quantities for Ozon, transit and home; `home_units=0` is a valid confirmed zero, while omission is invalid. The owner explicitly confirms that Ozon quantities include reserved units and that transit quantities are not already included in Ozon. Unknown or overlapping transit, unconfirmed stock semantics, fractional/negative counts, ambiguous layer order, and incomplete cost/zone input block preview. Each positive zone portion becomes an `OPENING_FIFO_ANCHOR` event with a separate location; zero-zone confirmations are retained as opaque digest references. The date-only cutoff remains a date and does not become an invented midnight timestamp. The preview is read-only; commit atomically creates the initial layer queue and projection, sets the stream `FIFO_READY`, and retains `INVENTORY_CUTOFF_UNRECONCILED` in the projection. Consequently the confirmed opening cost queue can support current/unit planning after later adapters, but it still cannot supply factual Period Profit COGS. FC10 never converts legacy cost history automatically and never backfills FIFO before the chosen cutoff.

FC11 adds schema v3 `fifo_cost_rate_changes`, a separate append-only history for owner-confirmed subsequent acquisition rates. The per-unit amount is the exact Decimal/RUB sum of purchase, delivery to the owner, and packaging. A date-only effective boundary and an explicit old-at-home remainder are required. This remainder is stored as owner reconciliation evidence; it is not added to the already anchored finite old layers. The rate preview is read-only, owner/store/SKU scoped, expires after ten minutes, and is replaced by a newer draft. Confirmation uses one transaction, stream revision and rate-sequence CAS, a stable idempotency key, and append-only source evidence. It preserves all old finite layer costs and quantities, records no new quantity, and marks the queue partial because the new purchase size remains unknown. The finite old queue continues to lead FIFO; the newly recorded rate is only the open rate after older known units. The unproven physical cutoff remains blocked for factual Period Profit. A first rate without an opening queue is allowed only from exact, complete, confirmed-zero FBO/reserved/transit evidence plus explicit owner home zero; it creates the stream and zero projection without a fake receipt, event, or layer, and also stays cutoff blocked. This special path does not treat missing stock rows, unknown transit, or an incomplete response as zero.

The opening command validates store/SKU plus a stable product identity; any malformed supplied identity is rejected rather than being dropped while another identifier remains. The source must use `OWNER_CONFIRMED_FIFO_CUTOFF`, include its capture timestamp, and every opening event must retain the same date-only cutoff/effective date with no invented `effective_at`.

`Q_old = Q_old_ozon + Q_old_transit_not_already_in_ozon + Q_old_home` is valid only when each component is disjoint and its provenance is accepted. Reserved units are not added as another location. They cannot be excluded as sold unless the source proves a physical outflow. Transit is not added to Ozon stock if already represented there. Unknown quantities remain unknown. A negative remaining layer or conflicting total is `FIFO_CONFLICT`, not zero.

Inventory transfers preserve the existing layer and total quantity. A new `COST_LAYER_RECEIPT` is created only for new-cost units whose quantity is explicitly supported. A new cost rate with unknown purchase quantity is represented as a price assumption for the next unit, not infinite inventory. It can support a clearly labeled unit scenario but cannot assert available stock or cover factual sales beyond reconciled known quantity.

The pure allocation engine receives events already ordered by a proven causal/effective order and consumes oldest confirmed layers first. It does not infer order from timestamps. FC04 keeps this core independent of storage and APIs and applies input caps of 100,000 finite layers, 100,000 replay events, 100,000 units per sale/return event, 250,000 combined sale-allocation/return-basis lines per replay, 1,000,000 units per active finite stream and 1,000,000,000.00 RUB per unit cost. The 64 KiB normalized event cap is enforced at the persistence boundary, not by this in-memory kernel. Only complete projections are returned; malformed iterators, over-limit collections, unsupported money/currency, insufficient confirmed quantity, or invalid return basis fail closed with an allowlisted code. For each sale, allocation-line quantities equal sale units and COGS equals the sum of allocation lines; period COGS equals the sum of selected sale allocations. A saleable return restores only the exact original layer allocation and does not rewrite the original sale COGS. Average COGS per unit is display-only. Allocation replay is deterministic for the same ordered event set, policy version and source fingerprints.

FC16 adds `FifoCostReplayService`, which establishes an order from exact timezone-aware timestamps or non-colliding date-only evidence, and requires each physical sale's stable source identity and confirmed cutoff bridge. It rejects ambiguous dates, duplicate identities, unsupported movements, incomplete sale coverage, confirmed-quantity exhaustion, and an open rate applied before its effective date. The repository does not trust a caller-provided preview hash: under `BEGIN IMMEDIATE` it rechecks source fingerprint, stream revision, allocation revision, cutoff and identity, rebuilds the complete expected FIFO result from append-only source rows, then compares every allocation line and total before writing. Finite layers and unknown-quantity open-rate costs use distinct append-only tables; an allocation references the stream revision it prices and becomes stale when the source stream changes. FC18 adds only exact owner-confirmed saleable returns, pinned to the full prior sale allocation; ambiguous partial split returns and open-rate returns stay blocked. FC19 admits owner-confirmed non-sale outflows only for an explicit reason and finite-layer impact; their estimate is stored separately from sale COGS, and incomplete acceptance/zone transfer is discrepancy-only or pool-neutral. Return COGS money gates are unchanged, and owner-side source/cutoff validation remains required before any Period Profit use. FC19's linked synthetic profile and full pytest are recorded in the implementation journal; they do not establish Ozon source readiness.

Legacy operational switches resolve by `effective_from <= as_of_date`. The mutable `product_costs` compatibility projection is refreshed only from the latest switch effective on the current date; a future-only switch never creates or replaces today's projection, and a late older entry cannot roll it back. Current `get_cost`/`get_all_costs` readers resolve against the current date dynamically, so an already recorded future change becomes active without a writer or process restart. Current-card and price-scenario caches include the current effective-cost date in their scope; an explicit same-day save continues to use the existing refresh action. If the only apparent legacy current value has the same amount/currency and timestamp as a future switch record, the old database cannot establish which value was written, so the resolver returns `PERIOD_PROFIT_COST_LEGACY_PROVENANCE_AMBIGUOUS` instead of treating the future rate as today's cost.

## 7. Cutoff bridge (mandatory factual gate)

The current sources do not yet provide a proven shared watermark from FBO stock snapshot to physical sale. The following contract must be implemented as a gate, not assumed complete:

1. Record an anchor capture interval and its exact store/SKU source scope; do not describe it as a server-atomic snapshot unless Ozon returns a verified server as-of/revision.
2. Classify each sale as already represented in the anchor or after it using an independently supported physical event time or a validated reconciliation protocol.
3. Deduplicate money recognition by stable sale identity (`posting_number + SKU`) and never consume an inventory quantity again for a reaccrual.
4. A pre-anchor physical outflow whose finance accrual appears later has zero post-anchor queue consumption. A post-anchor outflow consumes once. If the only available date is a finance accrual date and it cannot prove which case applies, return `INVENTORY_CUTOFF_UNRECONCILED`; do not expose factual FIFO COGS to Period Profit.
5. Returns, cancellations, losses and transfers are separate movements. Current stock deltas and return status alone never infer their cause or saleable recovery.

The synthetic case in `tests/fixtures_fifo_cutoff_gap_v1.json` is a contract fixture, not an observed Ozon response. A future owner-triggered sanitized diagnostic may validate source fields. Real seller requests and source snapshots are outside this development run.

## 8. Preview, commit, revisions, and replay

- Preview is read-only and binds to tenant/store/exact product identity, stream revision, policy version, source fingerprint, capture interval, request budget and normalized payload hash. Transient confirmation state is user-scoped, short-lived, one-time, and not valid after restart.
- Commit uses one SQLite `BEGIN IMMEDIATE` transaction for compare-and-swap (CAS), idempotency, event insertion and projection revision. Exact idempotent replay returns the prior result. Same key/different payload, stale expected revision, identity drift, incomplete source, or owner/store mismatch rejects without partial writes.

## FC21. Late-entry historical reconstruction preview

`FifoCostLateEntryReconstructionService` is read-only. It accepts only a saved draft for the exact tenant/store/product/SKU and requires the draft's expected stream revision plus the exact linked complete supply-evidence fingerprint. The draft's accepted act quantity is documentary evidence of the cited supply only; it is not the purchase total, remaining home stock, or a new FIFO layer.

Before replay, the repository requires one owner-confirmed opening anchor, an explicitly reconciled inventory/finance cutoff, a complete projection, and a bounded complete event set. Every event after the anchor must have supported type/date/order; sales also need complete trusted realization evidence and the same cutoff bridge. A date-only event on the candidate boundary is ambiguous. Unsupported event types, missing dates, stale stream/evidence, untrusted sales, multiple existing rate transitions (until FC23), incomplete finite-layer allocation, or an unreconciled cutoff blocks the preview. A blocked result identifies the evidence needed; it must never infer an old balance by reversing today's stock.

When all gates pass, the service replays a single hypothetical open rate at the owner-confirmed effective date and returns a clearly modelled candidate allocation/COGS plus stream/allocation/source fingerprints. It does not persist the candidate rate, movement, layer, allocation, or correction and does not alter Period Profit, tax, or profit. The result is suitable only as input to FC22's before/after impact preview and atomic append-only correction boundary; it is not a factual production result. ## FR10 addendum — 2026-11-09: partial return costing convention

The owner approved a deterministic convention for partial returns from a sale whose FIFO allocation spans multiple cost bases: when source evidence identifies the sale and return quantity but not individual units, assign the return to the latest original FIFO allocation lines first (reverse original allocation-line order). Subtract earlier accepted partial returns from that same latest-first capacity before assigning another return. This is a costing convention, not physical-unit evidence. A full-sale return preserves original allocation order. Restocking never rewrites the original sale COGS or bypasses the existing Return COGS authorization/recognition gates. Non-sale outflows remain separate from sales COGS.
