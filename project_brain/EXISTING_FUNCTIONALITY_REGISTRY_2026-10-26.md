# Реестр существующих функций бота

Дата проверки: 26.10.2026.
База кода: e879e6d7881a097f040e56d9962223525840917c; дерево соответствует актуальному main 89eb9224c3e9ec2126f58dc4d38794b33c2a2cc0.
Назначение: карта пользовательски достижимых возможностей и их доказательств для этапов Z03–Z20. Это инвентаризация кода/документов/тестов, а не подтверждение доступности внешнего API на живом магазине.

## Метод и ограничения

Главное меню сопоставлено с AssistantKeyboardService.build_main_keyboard, ветвления — с AssistantButtonHandlerService.handle, AssistantTelegramAdapter, TelegramCommandService, telegram_api_bot и руководством пользователя. Связанные экраны объединены только в пределах одного пользовательского сценария. Достижимый пользовательский путь отличён от внутреннего сервиса, который ещё не выставлен кнопкой. Источники и запись перечислены на уровне контракта; их точные суммы, полнота, неизвестные значения и границы повторного включения проверяются профильными этапами ниже. Список тестов — доказательство существующей проверки, но не утверждение, что всё поведение уже прошло текущую end-to-end приёмку.

## Подтверждённые исходные gaps реестра

1. docs/telegram-user-guide.md перечисляет только часть 16 кнопок главного меню. В нём отсутствуют описание внешних расходов, экспериментальных расчётов, обзора внимания, обзора товаров, решений по товарам и ряда legacy действий. При этом отдельные inline-help/build_telegram_help_response пути содержат команды и ссылки. Это подтверждённый documentation discoverability gap, не доказательство поломки runtime. Внести как F-03 в Z02 и согласовать основные руководства без дублирования.
2. Карта обнаружила широкую тестовую поддержку доменных сервисов, но это не удостоверяет все сквозные комбинации UI → запрос/запись → повторное открытие. Не добавлять тест только для строкового перечисления callback. Z14–Z16 выбирать конкретные пользовательские границы и добавлять регрессию только при подтверждённом пропуске.
3. Нет владельческого evidence для текущей живой сверки начислений, полного 56-дневного окна кросс-докинга и эксплуатации 24–72 часа. Эти ограничения уже записаны как E-01–E-03; в этом реестре не превращаются в дефекты кода.
4. Из доступных только read-only примеров нельзя подтвердить точность данных живого магазина. Synthetic acceptance остаётся инженерной проверкой, а не production acceptance.

## Изменения этапа

Реестр не создаёт сервисов и не меняет runtime. Необъявленный внутренний прототип не добавлен как доступная функция. F-03 направлен в Z02; прочие проверки привязаны к этапам, чтобы очередь оставалась конечной.
