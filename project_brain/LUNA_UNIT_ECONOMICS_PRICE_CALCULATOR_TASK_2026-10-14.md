Добавить в Telegram-бот сценарный калькулятор: выбрать товар своего магазина, подставить предполагаемую цену продавца и увидеть прибыль с одной успешной продажи и маржу при заданных расходах. ## 6. Переменное среднее баллов — обязательный контракт

Расчёт исторической доли:

`b = 100 × сумма подтверждённых баллов / сумма соответствующей общей выручки`

Числитель и знаменатель относятся к одному SKU, одной схеме/выборке и одному периоду. Для планирования одной успешной продажи использовать согласованную выборку положительных продаж; возвратные, отменённые и сторнирующие операции не смешивать с ней через net aggregates. В U00 установить семантику `sale_amount`/`bonus`: выручка знаменателя должна включать баллы согласно действующему контракту проекта. Не прибавлять bonus к уже включающей его выручке.

Обязательные требования:

- Не усреднять дневные проценты: дни с разной выручкой имеют разный вес.
- Не заменять данные SKU итогом всего магазина и не делить исторические баллы на новую/текущую цену карточки.
- Использовать существующий механизм чтения полных daily accruals и identity. Установить полноту охвата периода и дедупликацию. Повтор одного начисления не меняет среднее; конфликтующие дубли делают оценку unavailable. Реакруал одной продажи не должен считаться второй независимой продажей без подтверждённой семантики.
- Отсутствующий bonus не означает ноль только потому, что FinanceService начал агрегат с 0. При недоказанной семантике отсутствия/неполной выборке — unavailable. Явно наблюдаемый ноль допустим.
- При нулевой выручке, отсутствии продаж, отрицательных/неконечных суммах, баллах больше соответствующей выручки или неразрешённом SKU — не вычислять автоматический b. Запросить ручной процент, включая явный 0%.
- При неудачном чтении дня не выдавать оставшиеся дни за полные 28 дней. Первую версию держать простой: incomplete source → ручное значение; не вводить скрытое сокращение периода.
- Количество строк начислений не называется количеством проданных единиц. Для денежной доли denominator количества вообще не нужен. Можно показать «финансовых операций», а «штук» — только при подтверждённом quantity evidence.
- Период — 28 завершённых дат финансовых начислений, заканчивается вчера по действующему календарю магазина/проекта. Clock inject для тестов; UTC timestamp наблюдения не заменяет календарь начислений.
- Обновлять среднее при новом открытии с просроченным snapshot либо явной кнопке «Обновить данные». Изменение цены пересчитывает рублёвые баллы по прежнему b и не запускает сеть.
- Ручной b сохраняется после refresh; показывать новое историческое среднее как доступное исходное значение. Только действие «Вернуть среднее» снимает manual override.

Источник может быть недоступен на конкретном аккаунте/периоде. Не требовать платной Analytics подписки и не обещать live-полноту до фактической проверки. Существование полей в коде — техническая возможность, не доказательство полной выборки продавца.

## 7. Математическая модель и результат

`G = P` — предполагаемая общая выручка с одной успешной продажи, включая ожидаемые баллы.

`B = P × b / 100`

`K = P × c / 100` — комиссия при зафиксированной ставке.

`A = P × a / 100` — плановая реклама.

`F = K + L + M + E` — непересекающиеся учтённые расходы Ozon.

`profit_before_tax = G − F − C − A`

Вызвать TaxService с политикой магазина: `revenue=G`, `gross_profit=profit_before_tax`, `discount_points=B`, configured rates. Для USN_INCOME база — `G − B`; для других поддерживаемых режимов использовать действующий контракт TaxService, включая minimum tax. Не делать `revenue=buyer_price`, а затем ещё раз вычитать B. Не вычитать B второй раз из прибыли.

`profit = profit_before_tax − tax`

`margin = 100 × profit / P`

Маржа имеет знаменатель P; наценка на себестоимость не подменяет её. Результат также показывает налог ₽ и фактический налог % от P, сумму рекламы ₽, ожидаемые баллы и налоговую выручку. Убыточный сценарий — нормальный результат с отрицательной прибылью/маржой, а не validation error.

Реализовать чистую вычислительную функцию/сервис с валидированными входами и без I/O. Денежные значения считать с устойчивой десятичной точностью; повторно использовать TaxService и его округление. Не округлять b до отображаемых двух знаков до вычисления. В UI ₽ и % — два знака, разряды разделять пробелами, «−0,00%» нормализовать.

Контракт результата содержит: `kind=PRICE_PLANNING_SCENARIO`, user/store/SKU identity, scenario id/version, inputs с units/provenance, source periods/as_of/completeness, все calculated components, missing/invalid inputs, included/excluded scope, `read_only=true`, `executed=false`. Ни одно поле scenario не выдаётся за наблюдаемую прибыль или факт новой цены.

При неизвестном обязательном поле итоговая прибыль и маржа — unavailable с конкретным действием заполнения; частичные известные компоненты доступны. Decision 028 unknown advertising сохраняется: только пользовательский ввод делает плановую рекламу известной, не исторической.

Оба столбца пересчитываются тем же сервисом и с одинаковыми C/a/b/ставками/фиксированными расходами; это сравнение влияния цены, а не сравнение с фактической прошлой прибылью. Если P0 отсутствует, основной сценарий работает, сравнение unavailable.
6. Действия результата: «Изменить цену», «Параметры», «Обновить данные», «Другой товар», «Юнит-экономика/Главное меню». Refresh не отменяет введённые manual assumptions.

Пример короткого результата:


Результат по умолчанию укладывается в один короткий Telegram блок (целевой предел 3 500 UTF-16 units). Технические error codes, URL endpoints и raw records не помещать в обычный пользовательский экран. «Допущения» может показать подробные provenance/периоды без повторного HTTP.

## 9. Изоляция, состояние и границы сети

- Pending input, snapshot, результат и callback принадлежат `user + tenant/store + canonical SKU + scenario id/version`. Старое сообщение не меняет новый сценарий. Callback data ≤64 UTF-8 bytes.
- При смене/отключении магазина, отмене, выборе нового SKU или выходе из формы старое pending не принимается в новом контексте. Проверка origin store выполняется до любого запроса данных и до изменения сценария.
- Единичный read-only snapshot глубококопируется; scenario overrides не мутируют factual results, cache, shared source attributes или БД. Не использовать существующий unit-query cache с offer-only key без отдельной tenant-safe границы.
- Shared snapshot cache ограничен, с lock для get/expiry/store/eviction. Дефолт TTL 600 секунд, максимум 128 активных сценариев — инженерные настройки, доступные через constructor/config. После истечения TTL предложить новый snapshot; не выдавать старые ставки за актуальные.
- Первичная загрузка/refresh использует существующую инфраструктуру operation trace: кооперативный максимум **60 секунд и 64 реальных HTTP-попытки**, включая retries. Cached reads не считаются HTTP. Это предел, а не требование выполнить столько запросов. Пересчёт P/C/a/b выполняется без сети.
- Финансовый read-session/cache принадлежит tenant и запросу либо явно partitioned tenant-safe scope. Не расширять общий cache по date-only ключу на разные магазины. Новый worker должен сохранить ContextVar scope.
- Не загружать account-wide postings/returns/Performance для каждого изменения цены. Использовать существующие финансовые reads и узкий запрос карточки; failed automatic source не мешает полностью заполненному ручному сценарию.
- Одновременное открытие/refresh того же сценария дедуплицируется. Вход другого пользователя/магазина независим. Обработка текста согласует stage и допустимый status; повтор текста на экране результата/параметров возвращает действующие кнопки своей версии.

### U00 — результат аудита источников (2026-10-14)

Подробная карта источников и ограничения зафиксированы в [UNIT_PRICE_CALCULATOR_SOURCE_AUDIT_2026-10-14.md](UNIT_PRICE_CALCULATOR_SOURCE_AUDIT_2026-10-14.md). Ключевые подтверждения:

- `FinanceService.get_daily_finance(sku=...)` сохраняет `commission.sale_amount` как `gross_sales`; `commission.bonus` отдельно даёт discount points. Базовый агрегат не сообщает, что bonus был явно предоставлен для каждой подходящей продажи, поэтому его `discount_points=0` недостаточно для автоматической доли.
- Счётчик `sales_count` — число положительных строк товара в начислениях, не штуки. Он не используется для балльной доли и не доказывает расход на единицу.
- Текущая карточка даёт цену продавца и текущую FBO-ставку, но не тарифную котировку для новой цены. Фактическая текущая экономика использует отдельную налоговую политику buyer-price и не переиспользуется для сценарного налогового расчёта.
- Автоматическую долю баллов показывать только при доказанной полноте 28 завершённых дней, точной SKU-идентичности и явном bonus для каждого включённого наблюдения. В остальных случаях — ручной ввод, без подмены unknown нулём.
- Исторические расходы на доставку/выдачу/эквайринг из текущего агрегата не имеют достаточного подтверждения per-unit denominator. До появления подтверждённого quantity evidence просить ручные ₽/шт.; не переносить строковый средний показатель.
- Налоговую политику и формулы брать из tenant-scoped `TaxConfigurationService` и существующего `TaxService`. Реальное обновление источников должно использовать текущие operation trace и предел 60 сек./64 фактические HTTP-попытки.

Проверка исходного SHA `655b3a0` — существующие целевые finance/current-economics/tax тесты: **44 passed** (Python 3.12, `PYTHONPATH=app`). Live Ozon-источник конкретного магазина на U00 не проверялся. Полнота исторической выборки и SKU-scoped automatic `b` остаются условными до U02; ручной fallback обязателен.

## 11. Обязательные meaningful проверки

- Числовые фикстуры P=500/600, переменные ставки, нулевые и отрицательные итоги; маржа ≠ наценка; допустимая высокая себестоимость даёт убыток.
- Баллы уменьшены в налоговой базе ровно один раз; не вычтены ещё раз из прибыли и не прибавлены к уже включающей их выручке. Current buyer price не просачивается в scenario tax base.
- Налоговый режим/ставка берутся из того же магазина. NONE/USN_INCOME/поддерживаемый income-minus-expenses/minimum-tax соответствуют TaxService, unconfigured policy → unavailable.
- Weighted points ratio с неравными дневными выручками; explicit zero; отсутствие bonus, нулевая выручка, incomplete day, invalid sums, баллы >gross, conflicted duplicate, multi-SKU и неразрешённый архивный alias. Строки/операции не становятся штуками.
- При новой P комиссия/реклама/баллы/налог изменяются; C и подписанные fixed fees сохраняются. Последняя миля не вычитается второй раз. Процент эквайринга не выдумывается из несогласованных сумм.
- Локальный пересчёт нескольких цен не увеличивает число HTTP-вызовов. Refresh делает ограниченный новый read, сохраняет manual overrides, сброс b явно возвращает historical estimate.
- Empty history SKU: auto source unavailable, полностью ручной сценарий работает; unknown обязательный input не становится 0. Явные C=0/a=0/b=0 принимаются как допущения.
- Ввод `600`, `600,50`, `1 200,50`, пробелов/NBSP; отрицательная/нулевая P, NaN/Infinity/bool, неверные проценты и слишком длинный ввод отклоняются без потери рабочего сценария.
- Через production Telegram route: выбор → ввод → расчёт → изменение цены/стоимости/рекламы → результат; manual parameters; неверный текст → повтор → действующие кнопки; cancel/navigation и callback replay.
- Начать в магазине A, переключиться на B/отключить A, отправить цену или старый callback: отсутствует запрос/изменение сценария в B. Один SKU в двух магазинах и два пользователя не пересекаются.
- Старый result/callback A после нового scenario B не меняет B; concurrent refresh/update не смешивает snapshots. TTL, capacity и concurrent eviction не вызывают KeyError.
- Фактическая unit economics, Period Profit, product cost/history, tax configuration и Ozon price не изменены после серии сценариев. Тесты проверяют отсутствие repository/business writes и сетевых mutations.
- UI naming, grouped numbers, percentage denominator, source periods, unknown messages, callback length и Telegram size; production factory wiring получает ту же store policy и изолированный источник.

Точки регрессии existing consumers: `tests/test_product_unit_economics*`, `tests/test_current_unit_economics*`, `tests/test_guided_seller_cost_onboarding.py`, `app/tests/test_seller_cost_confirmation_flow.py`, связанные tax/tenant/Telegram routing tests. Для новых тестов использовать минимальные обезличенные fixtures, injected clocks/transports и контролируемые interleavings; не копировать пользовательские XLSX/.env в репозиторий.

## 12. Критерии готовности

1. Можно выбрать свой SKU и менять P/C/рекламу, получая воспроизводимую плановую маржу.
2. Средняя доля баллов получается автоматически только при подтверждённой выборке, изменяется вместе с периодом/refresh и применена к новой цене; предусмотрен manual override/fallback.
3. Все видимые расходы и происхождение понятны; не заявляется точный будущий тариф или полная прибыль магазина.
4. Налог следует согласованной модели проекта, отсутствующие данные не превращаются в нули, ставка Ozon и фактический финансовый результат не смешаны со сценарием.
5. Изменения сценария изолированы по пользователю/магазину/версии; нет записи в рабочие цены, расходы, себестоимость или tax policy.
6. Пересчёт мгновенный локальный; получение данных ограничено budget и snapshot cache.
7. Новые meaningful regressions и полный required CI нового code SHA зелёные, архитектурный review проведён, документация фиксирует фактическое состояние.

На момент создания исходного ТЗ реализация ещё не запускалась. Текущий статус выполнения приведён в этапах U00–U03 выше; live API конкретного магазина не запрашивался.
