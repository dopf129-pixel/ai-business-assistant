## 3. Обязательные инварианты

1. Ozon остаётся источником только для чтения. Не менять цены, рекламу, карточки, поставки, остатки или иное бизнес-состояние Ozon.
2. Использовать существующие `TaxService`, canonical Period Profit и калькулятор. Не вводить вторую формулу прибыли/налога. Пользовательские налоговые правила проверять как настройки продукта; не выдавать их за юридическое заключение.
3. Неизвестно, подтверждённый ноль, неполное покрытие и неприменимость — разные состояния. Не заменять ошибки/429/отсутствующие метрики нулями.
4. Нетто-начисления финансового источника сохраняют денежный авторитет. Строки детализации и сверочный Performance не вычитаются повторно. Не распределять общие расходы по SKU без подтверждённой модели.
5. Нельзя молча менять период, timezone, основу даты или смысл количества для получения совпадения.
6. Сохранённые v1/v2 планы остаются воспроизводимыми: только замороженные допущения, явное обновление в новую ревизию/копию, owner/store isolation, CAS, защита от старых callback.
7. Кросс-докинг: signed начисления с корректировками за 56 завершённых дней / фактически принятые cross-dock единицы; SKU и общая оценка магазина не складываются. Продажи не заменяют знаменатель. Неоднозначные multi-supply даты сохраняют incomplete.
8. Return COGS: статус возврата сам по себе не доказывает восстановленную себестоимость. Существующие recognition → authorization → commit → final application контракты сохранить. Не добавлять пользовательскую кнопку учётного commit и новые слои evidence без конкретной доказанной необходимости.
9. Пользовательский ввод себестоимости требует даты действия; применение ко всей истории — только после отдельного подтверждения. Не менять это правило ради сверки старого периода.
10. Ключи, Client ID, Telegram token, master key, `.env`, полные БД и сырые отчёты не входят в Git, CI artifacts, поддержку или сообщения модели. Не печатать окружение целиком.
11. Новая денежная логика использует Decimal, конечные значения, существующее округление и проверку числового равенства; формат `12.0`/`12.00` не является расхождением.
12. Исключить скрытую запись при импорте/построении диагностик. Некоторые repository-конструкторы открывают/создают БД: не строить production factory с реальной storage для проверки файлов.

- Расширять существующий read-only projection; не вводить независимую competing completeness pipeline.

**Готово:** есть ограниченный backlog B01–B05 с evidence; существующий рабочий функционал не заказан повторно.

### B01 — единый смысл суммы и степени подтверждения

- Для каждого материального компонента выводить сумму либо unknown, источник, период, coverage и краткую причину. Учитывать уже включённый в нетто расход, отдельно показанную расшифровку и только сверочную сумму.
- Различать observed zero, нет данных, частичный ответ, неприменимо, предварительную оценку. Неподтверждённое право доступа/подписку нельзя угадывать по отсутствующему полю.
- Сохранить публичные статусы существующих сервисов; при необходимости нормализации сделать совместимый view adapter и задокументировать mapping.
- Для нулевой выручки показать «доля недоступна». Избежать `-0,00%`; маленькая ненулевая сумма может отображаться как `<0,01%` с понятным знаком.

**Проверки:** ноль и unknown различаются во всех views/exports; смена магазина, TTL и старый callback не раскрывают чужой снимок.

### B02 — заказанные, отменённые и возвращённые единицы

- Сверить existing Analytics / FBO-FBS / returns paths с ранее полученной диагностикой. `cancellations` и `returns`, отсутствующие в metrics/totals, остаются unavailable.
- Считать по подтверждённому `product.quantity`, distinct ID и полной пагинации; не подменять количество единиц числом отправлений/строк.
- `Cancellation` и `ClientReturn` не складывать в «возвраты покупателей»; статусы движения возврата не заменяют его тип. Даты создания заказа, отмены и смены статуса возврата маркировать отдельно.
- Не строить историческое число отмен из текущего статуса отправления без доказанного фильтра периода. Если источник даёт лишь такую выборку, честно назвать её и сохранить ограничение.
- При новом source contract подтвердить официальный метод, фильтр, поля, пагинацию и лимиты; использовать уже подключённые adapters. Отчёт может подтвердить числа, но не семантику неизвестного API-фильтра.
- Если бесплатного пригодного источника нет, завершить инженерный этап явной недоступностью и инструкцией диагностики, не притворяясь, что данные появились.

**Проверки:** quantity > 1, повтор на соседних страницах, повторный статус, два типа возврата, частичное чтение, FBO+FBS, пустой полный ответ, неизвестный тип и граница периода.

### B03 — категории расходов и точное включение в прибыль

- Использовать общий accrual classifier. Комиссия — фактические финансовые суммы пригодного источника, не восстановление из процента; месячный realization и произвольный период имеют разные условия доступности.
- Показать размещение, прямую/обратную логистику, рекламу и кросс-докинг согласно подтверждённым именам/типам; не смешивать отправку покупателю и поставку на склад.
- Раскрыть остаток начислений до известного списка категорий с ограниченным экраном и полной выгрузкой. Подкатегории помечать «в том числе»; контрольная сумма исключает повторное вычитание.
- Performance CPC — сверка с отдельной датой/coverage; не второй расход поверх finance. Не обещать разбиение по кампаниям, если источник даёт только типы начислений.
- Проверить внешние разовые/периодические расходы через действующую форму и repository; отсутствие подтверждения полноты не становится «расходов нет».

**Готово:** итог нетто не изменён категоризацией; сумма разложения и остатка объяснима; одна операция учтена один раз.

### B04 — себестоимость и восстановление по возвратам

- Проверить даты действия и наличие себестоимости для разных SKU/исторических продаж; сохранить отдельное подтверждение применения ко всей истории.
- Через существующий blocker resolver показать что именно не позволяет учесть Return COGS: quantity/identity, historical cost, inventory recovery, attribution, recognition/authorization/commit и т. п.
- Давать только уже разрешённые действия владельца. Не объявлять цепочку завершённой по одному статусу `ReturnedToOzon`/`SALEABLE_RESTORED` и не добавлять учётный write consumer.
- При недостающих доказательствах показать подтверждённую часть/ограничение и влияние на итог; не рисовать точную чистую прибыль при неполной себестоимости.

**Проверки:** частичная себестоимость, смена даты, непригодный возврат, компенсация, stale evidence и подтверждённый завершённый существующий путь без повторного применения.

### B05 — приёмка полноты

- Составить matrix случаев полного/частичного/недоступного результата; проверить одинаковые причины в основном отчёте, деталях, поддержке и CSV/JSON.
- Все данные брать из одного снимка: открытие детализации/экспорта не вызывает новый financial request.
- Сохранить центральные расчёты, owner/store/period/source-basis и совместимость старых plans/callbacks.
- Вернуть результаты в A04 для повторной сверки. Закрыть подтверждённые defects отдельными небольшими commits, а ограничения источников оставить явно видимыми.

## 9. Модуль C — удобство ежедневной работы

### C00 — инвентаризация экранов и проект короткого отчёта

- Пройти основные пути по public handler tests: прибыль, экономика магазина, экономика SKU, калькулятор, сохранённые планы, внешние расходы, диагностика.
- Зафиксировать где отчёт перегружен, повторяет предупреждения, теряет период/SKU или предлагает лишнее действие. Проблему подтвердить текущим ответом, не старым скриншотом.
- До реализации записать схему основного экрана и кнопок. Основной финансовый ответ целиться в **1 500–2 500 символов**, без потери суммы/смысла/важного ограничения. Telegram предел проверять существующим transport по UTF-16, не только Python `len`.
- Подробности доступны через существующие scoped snapshot callbacks и export. На основном экране: период, ключевые суммы, степень полноты, одна важнейшая причина и понятные следующие действия.

**Готово:** схема экранов описана, не требует нового бизнес-решения, сохраняет доступ ко всей информации.

### C01 — компактный финансовый отчёт с детализацией

- Сделать единый стиль чисел с пробелами тысяч, рублями, процентом от общей выручки и корректными знаками. Доли количества считать от обозначенной количественной базы.
- Длинные источники, technical endpoint, диагностику, разложение остатка и второстепенные оговорки вынести в «Подробности»/существующую диагностику, привязанную к снимку.
- Прибыль без себестоимости явно так и назвать; предварительную ставку/частичную прибыль не делать визуально окончательной.
- Длинные детали разбивать/пагинировать через существующий механизм. Проверить emoji, большой список категорий и длинные названия; ошибка отправки не теряет действия/контекст.

**Проверки:** содержимое цифр не меняется; ключевое ограничение остаётся в компактном экране; основной экран укладывается в цель, каждый отправляемый message — в реальный лимит.

### C02 — понятные следующие действия и навигация

- Из строки неполноты вести к существующей форме: себестоимость, период, внешний расход, диагностика или явное обновление источника. Не предлагать невозможную кнопку «исправить API».
- Сохранить выбранный магазин/SKU/период и возвращать в исходный результат. Переход между магазинами сбрасывает несовместимый ввод.
- Повторное/старое подтверждение не сохраняет новый чужой черновик. Связать действия с owner/store/draft/version и проверить конкурирующие ответы.
- Учитывать прежнее пожелание владельца: в финальном выборе экспериментального отчёта не возвращать лишнюю кнопку «Выбрать другой период», если это уже исправлено.

**Приёмка:** владелец может исправить известный пробел и вернуться к расчёту без повторного ручного выбора товара; stale flow безопасно отвергается.

### C03 — ожидание, повтор и отмена

- Переиспользовать существующий progress feedback, inflight dedup и operation trace. Дубли одного действия не запускают несколько одинаковых расчётов.
- Показывать фактическое состояние: расчёт, неполное чтение, лимит/временная ошибка, готовый сохранённый снимок. Не писать «обновлено», пока новый результат не принят.
- Повтор/продолжение уважает общий бюджет и checkpoint; не обнуляет 56-дневное окно для каждого SKU.
- Отмена/уход в меню не оставляют поздний результат активным в другом магазине; не подменять старый snapshot новым молча.

**Проверки:** повторный клик, 429, timeout, отмена, store switch во время запроса и поздний callback.

### C04 — измерить и убрать лишнюю работу

- Зафиксировать baseline числа HTTP-попыток/финансовых пагинаций и времени на fake source для первого расчёта, тёплого повтора, деталей, экспорта и batch из 3 SKU.
- Детали/экспорт/открытие saved plan: **0 новых Ozon-запросов**. Один root batch использует общее окно и сбрасывает refresh один раз. Нельзя ускорять ответ скрытым обрезанием SKU/дней.
- Проверить текущие request/time limits, bounded TTL/cache size и tenant/window/model keys; производительность не оправдывает публикацию partial rate.
- Оптимизировать только измеренный лишний запрос/повторную обработку. Для времени использовать стабильную сравнительную методику, не flaky абсолютные пороги общего CI runner.

**Выход:** таблица до/после с числом вызовов и воспроизводимой командой; заявленное ускорение не распространяется на непроверенный live Ozon.

### C05 — сквозная пользовательская приёмка

- Public handler: расчёт → короткий отчёт → детали → исправление известного пробела → пересчёт → экспорт; калькулятор → сохранение → перезапуск сервиса → открытие исторического плана.
- Два магазина, несколько SKU, русские длинные названия, нулевая выручка, частичный источник, старый callback и ошибка доставки сообщения.
- Проверить существующие разделы меню и формат ручной даты. Обновить `docs/telegram-user-guide.md` точными пользовательскими шагами.

**Готово:** завершённые сценарии требуют минимум повторного ввода, сообщения понятны и transport не получает слишком длинный ответ.

## 10. Модуль D — резервные копии, обновление и эксплуатация

### D00 — карта пользовательских данных и границы снимка

- По коду инвентаризировать configured storage root, tenant-specific SQLite/JSON, legacy пути без env, seller costs, expenses, saved plans и credential ciphertext. Не читать настоящую `.env`/БД ради инвентаризации.
- Учесть, что некоторые данные находятся по историческим относительным путям; наличие `.runtime-data` не доказывает что все repositories используют только её. Каждый поддерживаемый путь должен быть явно охвачен или отмечен как unsupported.
- Описать что включается, что исключается и почему: `.git`, `.venv`, исходники, temp/cache/lock/process-control files и секреты не являются резервной копией бизнес-данных.
- Согласованный снимок нескольких файлов делать при подтверждённо остановленном собственном экземпляре бота. Не обещать cross-database consistency по одному `sqlite.backup()` работающего процесса.

**Выход:** storage manifest contract/version и стратегия проверки без нового storage framework.

### D01 — создание и проверка резервной копии

- Добавить одну локальную команду, например `backup_bot.ps1`, поверх узкого Python helper. По умолчанию она не останавливает бот скрыто: проверяет lifecycle и объясняет необходимость остановки. Updater сможет вызвать её после штатной остановки.
- Работать только с разрешёнными resolved paths; исключить reparse/symlink выход из заданного root. Назначение не должно пересекаться с исходными каталогами/файлами. Новая копия создаётся вне Git, например в явно gitignored `.local-backups/`; проверка доступа относится к новой копии, ACL исходных данных не менять.
- Записывать manifest: формат/версия, UTC timestamp, app revision, относительные paths, sizes, checksums и schema metadata без секретов. Публиковать completed marker только после успешной проверки/атомарного завершения.
- SQLite читать в согласованном режиме/через backup API и проверять `integrity_check`; JSON проверять на синтаксис и минимальный существующий контракт. Не исправлять повреждённый исходник автоматически.
- По умолчанию не включать `.env`, Telegram token и master key. Явно сообщить: encrypted Ozon credentials восстановятся только с исходным `OZON_CREDENTIAL_MASTER_KEY`; ключ владелец хранит отдельно безопасным способом.
- Не удалять старые копии автоматически в этом пакете. Ошибка диска/доступа не создаёт успешную запись и не повреждает предыдущую копию.

**Проверки:** все supported stores/legacy paths, пробелы/кириллица, disk-full/permission simulation, повреждённый JSON/SQLite, running bot, прерванное создание, секреты не попали в artifact.

### D02 — проверка восстановления в новый пустой каталог

- Добавить `restore_bot.ps1`/эквивалент: validate/dry-run и восстановление только в новый пустой каталог. Не перезаписывать действующую storage и не менять `.env` автоматически.
- До записи проверить manifest/version/checksums, лимиты размера/числа файлов, unsafe/absolute/`..` paths, дубликаты нормализованных Windows paths, symlinks/reparse и archive bombs. Повреждённая/неподдерживаемая копия отвергается.
- Восстанавливать в staging, затем валидировать все записи и пометить целостный результат. Проверить equality данных расходов/стоимостей/ревизий планов и tenant isolation.
- Отсутствие/несовпадение original master key — отдельный результат credential recovery, не ложный успех подключения Ozon. Для доказательства использовать только сгенерированные test-only ключи.
- Записать инструкцию владельцу по явному переключению storage root и возврату назад. Не запускать восстановление на настоящих данных в рамках разработки.

**Приёмка:** исходные тестовые данные → backup → новая директория → чтение существующими repositories дают те же бизнес-значения; источник и действующий target не меняются при любой ошибке.

### D03 — безопасный предварительный этап обновления

- Добавить `update_bot.ps1` с read-only `-CheckOnly` и понятным планом: текущая версия, ожидаемая target version, свой процесс, конфликты checkout, необходимость зависимостей и backup.
- Проверять фактический repository root/branch/tracking и разрешённый remote. Обычный supported путь — fast-forward `main` из настроенного origin; не выполнять произвольные refs/shell strings из Telegram или файла отчёта.
- До остановки бота обнаружить code changes, divergence, конфликтующие untracked files и входящие изменения защищённых data paths. Показать точные пути, безопасно остановить updater с ненулевым кодом; не делать stash/restore/reset/clean и не прятать конфликт.
- Изменённые legacy `data/tasks.json`/`data/users.json` могут сохраняться при обновлении только если incoming diff их не трогает и Git не будет их перезаписывать. Это проверить явно; не разрешать все dirty paths под видом данных.
- `-CheckOnly` использует только локальные сведения и не выполняет fetch, запись Git/worktree/data, установку зависимостей, остановку/запуск или Ozon-запрос. Он явно предупреждает, что cached remote refs могут устареть. Обычная команда обновления сначала делает fetch как отдельный обозначенный шаг, затем повторяет preflight на полученном immutable target SHA; не называть fetch режимом без записи.

**Проверки:** wrong branch, wrong root/remote, dirty code, безопасные data changes, изменённый upstream data file, untracked overwrite, divergence, offline Git; процесс при preflight-failure остаётся как был.

### D04 — одна команда обновления с достоверным результатом

- Supported owner command `./update_bot.ps1` выполняет успешный preflight → штатный stop только собственного token-bound процесса → проверенный backup → fast-forward update → установка нужных зависимостей → локальная проверка → запуск → подтверждение polling readiness.
- Переиспользовать `bot_instance_lifecycle_service`, start/status/stop. Не искать и не завершать все `python.exe`; не менять старый процесс другого checkout молча. PID/напечатанный «started» не доказывает готовность.
- Зафиксировать консервативный режим: обычная команда завершает обновление фоновым запуском; `-NoStart` обновляет без запуска. Реализация в разработке вызывает только mocks; реальный запуск выполняется позже владельцем.
- После `requirements.txt` изменения обновлять зависимости даже если старые `telegram/cryptography/dotenv` импортируются. Пакеты работающего `.venv` не менять до остановки; не помечать installation-success по одному наличию `.venv`.
- Для каждого шага проверять exit code, timeout и ожидаемый revision. После остановки повторно проверить состояние checkout и использовать именно target SHA успешного preflight, не произвольно сдвинувшуюся ссылку. При ошибке после остановки явно сообщить «бот остановлен/обновление не завершено», готовую recovery-команду и путь проверенной копии. Не делать автоматический откат/восстановление бизнес-данных.
- Повторный updater сериализован локальной блокировкой. Отсутствие updates не создаёт фиктивную новую версию; успешный результат содержит фактически запущенный revision и статус readiness.

**Проверки:** failure каждого шага, failed stop/backup/dependencies/start/readiness, два updater, stale process, уже актуальная версия; данные/ключи/backup сохранены, ошибочного success нет.

### D05 — состояние процесса и безопасная диагностика

- Расширить существующие status/build metadata/support surfaces при необходимости: app revision, mode, started at, actual lifecycle state и краткая причина последнего сбоя. Отдельно различать корректность local env и готовность Telegram polling.
- `runtime_healthcheck` остаётся без сети и скрытой инициализации seller repositories. Не запускать Ozon-проверку при каждом healthcheck.
- Логи/support export имеют allowlist, ограничение размера и безопасные коды. Не включать token, ключ, connection-control secret, `.env`, полный путь с идентификатором продавца или payload ошибки Ozon.

## 14. Протокол автономной работы и доказательств

После каждого этапа обновлять журнал: статус, base/head, изменённые файлы/контракты, что реально выполнено, команда/результат проверки, ограничения, следующий доступный этап. Небольшие тематические commits; не объединять переработку финансов с backup/update без необходимости.

Допустимые статусы: `NOT_STARTED`, `IN_PROGRESS`, `IMPLEMENTED`, `VERIFIED_OFFLINE`, `VERIFIED_WITH_REPORTS`, `NEEDS_REVIEW`, `EVIDENCE_REQUIRED`, `BLOCKED`, `USER_VALIDATION_PENDING`. `IMPLEMENTED` не означает «проверено», `VERIFIED_OFFLINE` не означает live API/эксплуатацию. Для уже реализованного этапа записать доказательство и проверку, не создавать косметическую переделку ради статуса.

После сокращения контекста читать журнал/актуальный diff и продолжать следующий доступный этап. Не начинать программу сначала и не повторять пройденные проверки без нового изменения/риска. Отсутствующее внешнее evidence фиксировать одним списком; продолжать независимые этапы.

Обращаться к владельцу только при необходимом бизнес-решении или блокере без безопасного обхода. Бизнес-решением являются изменение налоговой/учётной семантики, новая аллокация общих расходов или включение записи в Ozon/учётный commit. Выбор имени helper, структуры теста, оформления кнопки или локальной реализации backup при заданных ограничениях решать самостоятельно.

Любой доказанный дефект оформить как: воспроизведение → ограниченное исправление → meaningful regression → актуальный CI → self-review. Не расширять scope по случайным TODO и историческим незакрытым пометкам.
