# ТЗ для GPT Luna: законченный помощник выбора цены по прибыли с единицы

Дата: 26.10.2026. Статус документа: READY_FOR_EXECUTION, реализация не начата.

Журнал исполнения: `LUNA_PRICE_PROFIT_PER_UNIT_PROGRESS_2026-10-26.md`.

## 1. Задание и конечный результат

Развить существующий калькулятор цены в законченный пользовательский инструмент, который помогает выбрать цену продавца Ozon с **максимальной прибылью в рублях на одну успешную продажу единицы выбранного SKU** после учитываемых расходов, включая рекламу, комиссию и налог.

Пользователь должен пройти весь путь внутри бота:

1. Выбрать магазин и SKU.
2. Получить существующие исходные данные и увидеть, каких данных не хватает.
3. Подтвердить применимые комиссии для разных цен; при недоступном автоматическом источнике ввести ставки вручную.
4. Сравнить несколько цен и рекламных сценариев, включая цены по обе стороны тарифной границы.
5. Узнать, до какого рекламного расхода новая цена сохраняет или увеличивает прибыль с единицы.
6. Сохранить расчёт, вернуться к нему после перезапуска и изменить допущения.
7. Начать наблюдение за ценой, которую пользователь самостоятельно установил на Ozon; позднее собрать доступные данные за завершённые дни.
8. Сопоставить наблюдавшиеся варианты, увидеть качество данных и получить обоснованный, ограниченный этими данными вывод.
9. Выгрузить те же результаты и источники, которые показаны на экране.

Инструмент завершён, когда эти пути связаны в production composition, проверены на синтетических примерах и ошибках, документированы и находятся в PR с зелёным CI актуального SHA. Внешнюю проверку на магазине показать отдельно; не ждать её, чтобы закончить независимые инженерные этапы.

**Одного документа, набора чистых функций, ещё одной таблицы чувствительности или внутреннего сервиса недостаточно.** Нужны достижимый Telegram flow, долговременное сохранение подтверждённых пользовательских допущений и наблюдений, восстановление после перезапуска и ясные ограничения источников.

## 2. Уже принятые решения владельца

Эти вопросы повторно не задавать:

- Оптимизируем **рубли прибыли с единицы**, а не процент маржи, выручку, количество заказов или суммарную прибыль за день.
- Цена сценария — **цена продавца в Ozon**, не цена покупателя после скидок Ozon.
- Себестоимость и рекламу пользователь может менять в плане; фактическая история от этого не меняется.
- При снижении цены рекламная эффективность может улучшиться и компенсировать потерю маржи до рекламы. Это проверяемая гипотеза, а не автоматическое правило.
- Комиссия может скачкообразно изменяться на границе ценового диапазона. Для каждой цены требуется заново выбирать применимую ставку.
- Числа 14% и 20% из прежней беседы **не подтверждены как актуальный тариф** и не должны становиться рабочими значениями по умолчанию.
- Если бот не подтвердил комиссию, пользователь должен иметь возможность ввести её вручную, в том числе разную для нескольких диапазонов.
- Ручные ставки нужно сохранять для конкретного owner/store/SKU/схемы, показывать их происхождение и позволять менять позже.
- Применение цены и изменение рекламы на Ozon выполняет сам пользователь. Бот анализирует и готовит рекомендации.

Объём продаж, выручку и прибыль за день показывать как сопутствующие показатели. Не использовать их скрытым коэффициентом ранжирования вместо выбранной цели.

## 6. Определение результата и финансовая модель

### 6.1. Целевая функция

Для сценария `s`:

`unit_profit(s) = canonical_forward(s).profit`

Forward включает цену продавца, соответствующую этой цене комиссию, себестоимость, рекламу, действующую модель баллов/налога, логистику/последнюю милю/эквайринг и известный кросс-докинг. Непокрытые расходы выводятся явно.

Ранжировать по прибыли **в ₽/шт.**, не по марже и не по дневной сумме. При равных значениях после принятого денежного округления показать равенство. Текущий вариант можно оставить первым как UI tie-break, но не объявлять более прибыльным из-за объёма продаж.

Название основного планового результата: «Плановая прибыль с единицы после учтённых расходов». Не обещать бухгалтерскую чистую прибыль и глобально оптимальную цену.

### 6.2. Три разных основания чисел

| Основание | Что разрешено утверждать |
|---|---|
| `SCENARIO_ASSUMPTIONS` | Лучший из рассчитанных сценариев при перечисленных допущениях |
| `MODELLED_FROM_OBSERVED_INPUTS` | Лучшая оценка по модели с наблюдавшимися входами; фиксированные/ручные расходы и ограничения остаются видны |
| `CANONICAL_FACT_COMPARABLE` | Сопоставление фактической прибыли с единицы возможно только при доказанной полноте и совместимости canonical evidence |

Исторический CPC-отчёт сам по себе не переводит наблюдение в `CANONICAL_FACT_COMPARABLE`. Показать доступную сумму/оценку и причины ограничения. Успешная разработка допускает честный `INSUFFICIENT_DATA` для конкретного магазина, но все поддержанные ветки должны работать и быть проверены.

Не смешивать эти основания в одном рейтинге. Для предположения использовать «при таких условиях»; для наблюдения — «в этих периодах»; причинный вывод «цена снизила ДРР» без отдельного доказательства не делать.

### 6.3. Округление и количества

- Денежная арифметика — Decimal, текущий ROUND_HALF_UP и копеечная сетка. Компоненты округляются так же, как в canonical forward.
- Сначала рассчитать компоненты, затем итог; не использовать rounded display rate обратно в расчёте без явного квантования.
- `advertising_per_unit = подтверждённый расход / совместимое количество единиц`, не количество строк, заказов или рекламных конверсий.
- Если по кампании известно число заказов, назвать показатель стоимостью заказа, не стоимостью единицы.
- В наблюдениях агрегировать суммы и единицы; не усреднять дневные ДРР или прибыли с единицы простым средним.
- При Q=0 прибыль с единицы неизвестна. Расход при нулевых продажах сохраняется отдельно; не присваивать нулевую удельную прибыль.
- Процент изменения прибыли не показывать от нулевой/отрицательной базы; разницу в ₽/шт. показать всегда при сопоставимости.
- ДРР от рекламно атрибутированной выручки и ДРР от общей выручки SKU — разные метрики. Обязательное поле `revenue_basis`; смешение запрещено.

## 7. Комиссия: диапазоны, автоматический источник и ручной ввод

### 7.1. Нормализованное правило

Каждая версия профиля содержит:

- owner_id, store_id, точную identity товара: product_id/offer_id/SKU, схему продаж;
- profile_id, revision/state_revision либо эквивалентный существующий CAS-контракт;
- `price_basis=SELLER_PRICE_RUB`, валюту RUB;
- интервалы в целых копейках с **включёнными** нижней и верхней границами;
- ставку в %, тип источника и фактически доказанную область применения;
- effective_from/effective_to, recorded_at/observed_at, source reference/version при наличии;
- origin: confirmed API/range source, current-price point, manual seller assumption;
- сведения о применимых скидках только если их условия доказаны или явно заданы как допущение.

Ставки хранить десятичным значением/строкой, не двоичным float. Названия полей адаптировать к стилю проекта, смысл сохранить.

Ноль процентов допустим только как явное значение. Missing/invalid/expired/unsupported/ambiguous отличаются. NaN, Infinity, bool, отрицательные ставки и ставки >100% отклонять.

Диапазоны могут иметь пробелы: цена в пробеле получает `COMMISSION_UNKNOWN`. Пересечения, включая общую включённую границу, отклонять. Не выбирать «первую» ставку из конфликтующих правил. Цену за пределами подтверждённого диапазона не рассчитывать по ближайшему тарифу.

Порог 100 ₽ принадлежит тому интервалу, который подтверждён источником/пользователем. UI может предлагать удобный шаблон «до 100 ₽ включительно / от 100,01 ₽», но это не универсальное правило всех тарифов.

### 7.2. Автоматический источник

1. В Q05 проверить действующие официальные API/docs и существующий ответ цен. Зафиксировать endpoint, поля, дату и scope доказательства.
2. Если ответ содержит только комиссию при текущей цене, сохранить именно `CURRENT_PRICE_POINT`: он не подтверждает комиссию для 95 ₽, 101 ₽ или всей категории.
3. Если надёжного источника сетки нет, закончить адаптер со статусом `RANGE_SOURCE_UNAVAILABLE`, рабочим ручным fallback и документацией ограничения. Не останавливаться и не выдумывать endpoint.
4. Не скрейпить личный кабинет и не добавлять runtime browser automation. Официальные тарифы можно нормализовать в подтверждённый versioned reference только если проверены применимость, дата и источник обновления; сетевые чтения не делать на каждую цену.
5. Если скидка зависит от ещё неизвестной локальности будущего заказа, не выдавать точную окончательную комиссию. Разрешить явно подписанный сценарий с базовой/ручной ставкой и показать условие.
6. Устаревший автоматический тариф не превращать в ноль; показать дату и действие «Обновить» / «Ввести вручную».

### 7.3. Ручной путь — обязательная законченная функция

Путь: «Комиссия не подтверждена» → «Ввести вручную» → границы диапазона → процент → следующий диапазон или preview → подтверждение → сохранение.

Минимум:

- одна ставка только для выбранной цены или несколько явно заданных диапазонов;
- ввод десятичной запятой/точки и привычных пробелов в ценах;
- preview с конкретным SKU, схемой, диапазонами и датой действия;
- сохранение после явного подтверждения в локальный planning scope;
- «Изменить», «Использовать только в этом расчёте», «Повторить получение из Ozon»;
- отмена и повторная кнопка не создают второй записи;
- старая кнопка не сохраняет новый черновик другого товара/магазина;
- ручная версия не перезаписывается автоматическим refresh молча;
- перед заменой ручной версии подтверждённой автоматической показать разницу и запросить подтверждение;
- неподтверждённая комиссия кандидата получает точечную кнопку заполнения, не сбрасывая сравнение.

В каждом результате показать «Комиссия X%: Y ₽ — введена пользователем» либо подтверждённый источник и дату. Не требовать повторного ручного ввода после перезапуска, если scope/date/профиль всё ещё применимы.

### 7.4. Версии и совместимость

Сохранённый вариант содержит выбранные правила/ставку, основания и версию расчёта как frozen projection. Один живой profile_id без зафиксированной версии недостаточен.

Старые v1/v2 планы открываются с исходным результатом, без сетевых чтений и ретроспективного пересчёта. Старую ручную ставку без диапазона сохранить как историческое допущение, не развернуть автоматически на новые цены. Продолжение нового сравнения предлагает подтвердить применимость.

Если нужна новая schema/calculation version, добавить совместимый reader и явный upgrade через новую revision/copy. Не мигрировать старые суммы на чтении. Изменение тарифного профиля не меняет существующие наблюдения, планы или отчёты.

## 8. Сравнение цен и эффект компенсации рекламы

### 8.1. Варианты

Новый помощник принимает 2–10 явных цен или ограниченный диапазон/шаг. Старый public parser 2–5 цен не ломать; новый ввод может иметь отдельный контракт.

Для каждой цены:

- получить комиссию через единый resolver;
- использовать один frozen набор остальных исходных предположений;
- сохранить ручной рекламный сценарий/подтверждённое наблюдение с правильным основанием;
- вычислить прибыль тем же forward и показать компоненты, маржу и отличие от baseline;
- отметить пропуски/неполноту; не выдавать недоступный вариант за убыточный или нулевой.

Первый режим рекламы — одинаковая явно выбранная ДРР для всех цен, с подписью «сценарий неизменной ДРР». Второй — отдельная ДРР для каждого варианта. Третий — наблюдавшийся расход на совместимую единицу, если его корректно поддерживает существующая модель. Смена режима показывается явно, расходы в ₽ и % не вычитаются одновременно.

Если расход в ₽/шт. переводится во внутреннюю ставку для существующего forward, сохранять исходную сумму и достаточно точную Decimal-ставку, проверять обратное совпадение денежного компонента до копейки. Округление внутренней ставки до двух знаков может изменить расход и запрещено как скрытая потеря точности. Если текущий контракт не обеспечивает точный перенос, расширить его совместимо или показать ограничение этого режима, сохранив рабочие режимы ДРР.

Отсутствие данных о зависимости рекламы от цены не мешает таблице условий, но запрещает утверждать, что какая-то неизвестная будущая ДРР обязательно наступит.

### 8.2. Порог компенсации

Для baseline `profit0` и candidate price `P1` найти два порога:

1. максимальный рекламный расход/ДРР, при котором `profit1 >= profit0`;
2. максимальный расход/ДРР, при котором `profit1 > profit0` после денежного округления.

Это не существующий лимит безубыточности и не обязательно целевая маржа. Использовать тот же forward и налог; простое вычитание «прибыль до рекламы − целевая прибыль» допустимо только там, где налог и остальные компоненты действительно не зависят от рекламы. Не менять налоговую политику ради простой формулы.

Для каждого найденного порога сделать конечную прямую проверку и проверить соседний доступный шаг. Показать сетку процента 0,01 пп. или согласованную точную сетку текущего ввода, денежное округление и статус точности. Если строгий рост недостижим даже при рекламе 0%, показать это явно.

### 8.3. Поиск и тарифные скачки

- Поиск по цене ограничен выбранным пользователем интервалом и не является доказательством глобального оптимума.
- Максимум 200 явных цен в одном локальном поиске, не более 20 тарифных правил и 1 024 forward evaluations на пользовательское действие, включая проверки. Не расширять существующие денежные пределы.
- Компенсационный порог запрашивается для выбранного кандидата; не запускать отдельный solver для каждой из 200 точек автоматически. Повторные локальные вычисления используют готовый snapshot и общий счётчик действия.
- Автоматически добавить в допустимом интервале цены на границах тарифов и ближайшие копейки с обеих сторон; итоговый лимит сохраняется. Если полный набор не помещается, предложить сузить диапазон, не обрезать молча.
- В пределах проверенного сегмента можно применять существующие методы только при доказанной нужной монотонности. Между сегментами сравнивать результаты отдельно.
- Прежний бинарный поиск целевой цены через скачок комиссии запрещён. Минимальная цена для цели — минимум валидных кандидатов по всем покрытым сегментам, с прямой проверкой.
- Если часть интервала не покрыта ставками, результат «лучший среди рассчитанных», с перечислением пропусков; не «лучшая цена во всём диапазоне».
- Для сетки показать фактический шаг. Максимум на сетке не называть точным максимумом между её точками.

## 9. Наблюдение за ценой и сбор данных

### 9.1. Пользовательский сценарий

«Проверить эту цену» → preview выбранного SKU/цены/версии плана/комиссии → пользователь подтверждает, что цену установит или уже установил самостоятельно → локальная запись наблюдения.

В карточке: плановая цена, начало и завершение, статус подтверждения цены, baseline, кнопки «Собрать результат», «Закончить», «Добавить заметку», «Сравнить», «Архивировать».

Начало наблюдения не означает, что бот изменил цену. Фактическое начало определяется подтверждённым effective timestamp или ручным утверждением с соответствующей маркировкой. Изменение цены в середине дня не делает весь день принадлежащим новой цене.

### 9.2. Что собирать автоматически по кнопке

В пределах подтверждённых контрактов:

- полные завершённые дневные интервалы и их timezone/date basis;
- доступную историю seller price из реальных строк продаж/подтверждённого исторического источника;
- buyer price/долю баллов, если источник действительно их различает;
- подтверждённые проданные единицы, отдельно заказанные/отменённые/возвращённые единицы с их периодом и основанием;
- суммы выручки, доступную attribution расходов, рекламу по SKU и её payment scope;
- известные остатки/периоды отсутствия товара, изменения рекламы/стоимости/налога — только при реальном evidence;
- время сбора, coverage и сведения о корректировках/незавершённых данных.

Сначала переиспользовать существующие canonical adapters. Не требовать от пользователя raw JSON для штатной работы и не объявлять CPC полной рекламой кабинета.

Сейчас `PeriodProfitSkuAdvertisingService` загружает CPC и не подтверждает остальные типы. При наличии неопределённых/неатрибутированных расходов разрешено показать CPC-метрики или модель с явно указанным scope; запрещено подписывать их «полная прибыль после всей рекламы».

### 9.3. История цены и смешанные периоды

- Текущая карточка подтверждает цену только в момент чтения. Два одинаковых чтения не доказывают отсутствие промежуточных изменений.
- Если в продажах отсутствует seller price с доказанной семантикой, сохранить `PRICE_HISTORY_UNCONFIRMED`; разрешить ручное утверждение пользователя как допущение, но не как API-факт.
- Запланированная цена и фактически подтверждённая цена хранятся отдельно.
- При разных ценах в одном окне маркировать `MIXED_PRICES`; не приписывать всю прибыль одной цене. Разделение допускается только при корректном распределении сопоставимых расходов; иначе предложить другое окно.
- Отмена/возврат по дате статуса, рекламная конверсия по окну атрибуции и финансовое начисление по дате начисления — разные основания. Не склеивать их в одну когорту без доказательства.
- Период с неподтверждённой историей остаётся полезной моделью/наблюдением с ограничениями, но не доказательством влияния цены.

### 9.4. Период и объём наблюдений

Начальные технические настройки: окно сравнения 7 завершённых дней для каждого варианта, ориентир малой выборки — менее 30 подтверждённых единиц на вариант. Пользователь может изменить эти значения в ограниченном контрактом диапазоне: 3–56 завершённых дней и 1–10 000 единиц.

Это условия удобства/предупреждения, не статистическое доказательство и не обещание достаточной мощности. Показать количество дней/единиц, причины несопоставимости и предупреждение о малой выборке. Не генерировать «вероятность победы 95%», «эластичность доказана» или confidence score без обоснованной методики.

Для стандартного сравнения предлагать одинаковую длительность и сопоставимый состав дней недели. Разные длительности можно отобразить отдельно с ограничением сравнения; не подгонять даты автоматически ради победителя.

### 9.5. Записи и обновление

- Наблюдения и версии результатов — отдельные локальные analytical/planning records в существующей tenant SQLite, не новая фактическая бухгалтерия.
- Один SKU не может случайно получить два активных конкурирующих наблюдения на одинаковый scope/window. Повтор нажатия идемпотентен.
- Изменение заметки/статуса/дат защищено expected state revision. Старый callback не завершает другое наблюдение.
- Повторный сбор после исправления Ozon добавляет новую версию результата; ранее сохранённые версии не переписываются.
- Пересекающиеся окна не объединяются в выборку с двойным счётом. При сравнении это отдельная причина ограничения.
- Локальное открытие, пагинация, экспорт и сравнение сохранённых результатов не делают сетевых запросов. «Обновить данные» — отдельное явное действие.
- Стартовые пределы: 100 записей наблюдений на магазин, 20 версий результата на запись, 64 KiB нормализованных данных на версию; превышение — понятная ошибка без потери истории.

## 10. Рекомендация по выбору цены

Вывод должен отвечать: какая из рассмотренных цен даёт большую прибыль с единицы, на каком основании и что ещё неизвестно.

Примеры корректных формулировок:

- «При введённой ДРР 12% вариант 95 ₽ даёт на 1,31 ₽/шт. больше базового. Будущая ДРР не подтверждена».
- «В сопоставленных периодах модель по наблюдавшимся входам показывает больший результат при цене X; Y проданных единиц, Z завершённых дней. Часть расходов оценена».
- «Выбрать лучший наблюдавшийся вариант пока нельзя: история цены не подтверждена / расход рекламы неполный / условия различаются».

Обязательные данные вывода: baseline, цена кандидата, прибыль с единицы, разница в ₽, комиссия и её origin, рекламный расход/ДРР и denominator, основание результата, период/количество/качество и ограничения.

Снижение CPC/рост конверсии можно показать как наблюдение, если поля есть. Выручку рекламного кабинета не приравнивать seller revenue. Любая оценка зависимости цены и ДРР из двух периодов помечается как наблюдаемая связь; изменения бюджета, размещения, трафика, остатков и скидок видны как возможные причины различий.

Если данных недостаточно, дать конкретное достижимое действие: заполнить комиссию для цены, задать рекламный сценарий, выбрать полные даты, собрать свежий результат или продолжить наблюдение. Не превращать отказ рекомендации в тупиковый экран.

## 11. UI, сохранение, exports и эксплуатация

- Вход через существующие «Юнит-экономика» → SKU → «Подобрать цену»; новые функции связать с калькулятором и «Моими планами». Не добавлять несколько конкурирующих главных меню.
- Первый экран короткий: выбранная цель, baseline, главный недостающий параметр и 2–4 следующих действия. Подробные компоненты и происхождение — отдельная кнопка.
- Таблица сравнения: цена, комиссия %, комиссия ₽, реклама ₽/шт./ДРР, прибыль ₽/шт., разница и статус. Суммы с пробелами тысяч; маржа не затмевает целевую прибыль.
- Если цена пересекает границу, объяснить скачок комиссии прямо в сравнении.
- Все изменения постоянного ручного профиля и наблюдений проходят preview/confirm. Сценарное редактирование остаётся локальным до сохранения.
- Просмотр сохранённого плана показывает дату/версию тарифа. Обновление не подменяет frozen результат.
- Новый экспорт содержит ту же нормализованную модель, границы, версии, статус и причины. Owner CSV/JSON могут содержать его SKU; support export не расширяется этими бизнес-данными.
- Сохранить UTF-16 лимиты Telegram, единый splitter и клавиатуру на последней части; не усекать суммы или причины молча.
- Пользовательские названия/заметки защищены существующими CSV formula и document guards.
- Callback содержит короткий ticket/version, не JSON, суммы, credentials или полные API payload.
- Source refresh одного действия наследует общий budget текущего `PeriodProfitOperationTrace`: ориентир 60 секунд / 64 HTTP-попытки существующего single-SKU пути, включая retries и Performance polling. Если нужен иной предел, обосновать в журнале и не увеличивать его незаметно.
- При неизвестном/неполном источнике сохранять ранее подтверждённые данные и статус нового сбора; не публиковать частичный refresh как готовый снимок.
- Новые tables/версии должны корректно попадать в существующий SQLite backup/restore; обратную совместимость проверить на старой БД.

## 12. Числовая приёмка и обязательные сценарии

Все ставки ниже **синтетические тестовые значения**, не действующие тарифы Ozon. Реальные отчёты владельца и идентификаторы не помещать в Git.

### N01. Компенсация рекламой, контрольный пример пользователя

Подготовить canonical fixture: себестоимость 20 ₽, логистика 20 ₽, последняя миля 0 ₽, эквайринг 4,06 ₽, кросс-докинг явно 0 ₽, баллы явно 0%, налоговый режим `NONE` (налог 0%), синтетическая комиссия 24,20% на обе цены. Это только синтетическая настройка, не изменение политики магазина.

| Цена | ДРР | Комиссия | Прибыль до рекламы/налога | Реклама | Прибыль |
|---|---:|---:|---:|---:|---:|
| 100,00 | 16,50% | 24,20 | 31,74 | 16,50 | 15,24 |
| 95,00 | 12,00% | 22,99 | 27,95 | 11,40 | 16,55 |
| 95,00 | 16,50% | 22,99 | 27,95 | 15,68 | 12,27 |

Разница успешного сценария: +1,31 ₽/шт.; относительная разница около +8,60%. В последней строке 12,27, а не 12,28: canonical calculator округляет компонент 15,675 до 15,68 ROUND_HALF_UP. Не копировать упрощённое округление из прежней беседы.

### N02. Порог нехуже и порог строго лучше различаются

Для baseline 15,24 ₽/шт. и цены 95 ₽ в N01:

- ДРР 13,38% → реклама 12,71 ₽ → прибыль 15,24 ₽: не хуже;
- ДРР 13,37% → реклама 12,70 ₽ → прибыль 15,25 ₽: строго лучше;
- ДРР 13,39% → реклама 12,72 ₽ → прибыль 15,23 ₽: хуже.

Показать оба порога и квантование 0,01 пп. Не выдавать равенство за рост прибыли.

### N03. Скачок тарифа

Синтетический профиль `[0,01; 100,00] → 11%`, `[100,01; 300,00] → 22%`:

- P=100,00: комиссия 11,00 ₽, после комиссии 89,00 ₽;
- P=100,01: комиссия 22,00 ₽, после комиссии 78,01 ₽;
- P=101,00: комиссия 22,22 ₽, после комиссии 78,78 ₽.

Resolver выбирает обе границы точно, comparison объясняет скачок, target solver не пропускает лучший кандидат нижнего сегмента. Добавить отдельный пример с достижимой целью в нижнем сегменте, недостижимостью сразу после скачка и повторным достижением выше.

### N04. Правила, пробелы, пересечения и неизвестность

- Цена в пробеле между правилами → неизвестная комиссия, кнопка ввода.
- Пересечение и конфликт источников → отказ, не первая запись.
- Current-price point для P=100 не подтверждает P=99/101.
- Явная ставка 0% валидна; отсутствующая, NaN/Infinity/True — нет.
- Ставка для другой схемы, owner/store/SKU/date никогда не применяется.

### N05. Ручной профиль и безопасность UI

Ввод двух диапазонов → preview → confirm → restart/reopen → использование в новом расчёте. Затем изменение профиля не меняет старый план. Повтор confirm даёт одну запись. Старая кнопка товара A/магазина A не сохраняет профиль черновика B.

### N06. Сохранённые планы

Существующие v1/v2 fixtures читаются без нового API и пересчёта. Новый план содержит frozen тариф и основание рекламы; refresh создаёт новую revision/copy с подтверждением. Unknown future version не переписывается.

### N07. Агрегация наблюдений

Два дня: расход 100 ₽ и 100 ₽, единиц 10 и 30. Общий расход на единицу = 200/40 = 5 ₽, не среднее дневных 10 и 3,333... ₽. Отдельно проверить Q=0 с расходом, несколько единиц в заказе, дубликаты и пересекающиеся окна.

### N08. Разные основания ДРР

Расход 100 ₽, общая seller revenue 1 000 ₽, рекламно атрибутированная выручка 400 ₽. ДРР по этим основаниям — 10% и 25%; значения не заменяют друг друга и не подставляются в один сценарий без приведения доказанного основания.

### N09. Неполнота и смешанная цена

Полный CPC + неизвестный CPO → только CPC/ограниченная модель, не полная прибыль. Две текущие одинаковые цены без исторических продаж не подтверждают цену всего окна. Смешанные цены, иные tax/cost/fee scopes, разные даты событий и неполные количества блокируют соответствующую фактическую рекомендацию.

### N10. Цель именно прибыль с единицы

Вариант A: 20 ₽/шт. и 100 единиц; B: 18 ₽/шт. и 200 единиц. При совместимом основании A выше по выбранной цели, хотя дневная/общая сумма B больше. При равных 20 ₽/шт. — равенство. Проверить отрицательные и нулевые результаты и запрет ложного процента роста от неположительной базы.

### N11. Налог и остальные компоненты

Налог с дохода, с прибыли и минимум проверяются существующим TaxService. Порог рекламы находится forward-методом даже когда изменение рекламы меняет налог. Кросс-докинг и последняя миля не вычитаются дважды. Историческая себестоимость берётся с действующей даты.

### N12. Budget, состояния и приватность

429/timeout/отмена/частичная пагинация не публикуют полный snapshot. Локальное сравнение 200 цен делает 0 внешних HTTP-запросов. Старый результат другого магазина не появляется после store switch. Export не делает refresh. User input с формулами/управляющими символами не обходит guards.

### N13. Restore и изменения источников

Создать тариф, план, наблюдение и две версии результата в синтетическом tenant; сделать backup/verify/dry-run/restore в новый root. Проверить идентичные данные, scope, версии и последующее чтение. Старый DB без новых таблиц открывается; потеря доступа/ошибка транзакции не оставляет полусохранённую запись.

### A — база и контракты

**Q00. Зафиксировать чистую базу.**

- Проверить ветку, diff, untracked, main/PR и его checks. Выбрать безопасный worktree и новую codex-ветку.
- Записать base/head, расположение source/test storage и запрещённые пользовательские файлы.
- Критерий: существующая работа не изменена, стартовая точка однозначна, журнал создан/обновлён.

**Q01. Короткий предметный аудит.**

- Сопоставить реальные handlers/services/schema с картой раздела 4. Выписать ровно отсутствующие контракты.
- Зафиксировать текущие формулы, округление, parser limits, old-plan поведение и source scope рекламы.
- Критерий: небольшой audit в журнале/отдельном документе с подтверждёнными ссылками; без переписывания рабочего кода.

**Q02. Изолировать проверки.**

- Использовать отдельный venv/temp/storage; dotenv отключить, Telegram/Ozon credentials очистить только в окружении тестового процесса.
- Проверить baseline относящихся тестов и hashes tracked/runtime baseline до/после.
- Критерий: воспроизводимый запуск без owner data. ACL/temp сбой отличён от дефекта кода; сохранены actual command/result.

**Q03. Утвердить контракты внутри реализации.**

- Описать objective, tariff scope, advertising basis, три основания результата, состояния доступности, snapshots и limits.
- Выписать публичные потребители и маленькие контракты между resolver → canonical forward → comparison → observation/recommendation.
- Добавить новое architectural decision только для реального расширения ownership/persistence/versioning, не для каждого helper.
- Критерий: бизнес-решения раздела 2 соблюдены, нет второго финансового pipeline и неопределённого слова «оптимальная».

### B — комиссия

**Q04. Чистый resolver диапазонов.**

- Реализовать точные границы копеек, даты, схему, scope, приоритет явно выбранного профиля и controlled unknown/conflict.
- Проверить N03/N04 и числовые/размерные limits.
- Критерий: тесты не требуют Telegram/Ozon/DB; точечный тариф не расширяется автоматически.

**Q05. Автоматический источник и доказательство применимости.**

- Сверить официальные актуальные contracts и существующие ответы. Подключить только подтверждённый read-only источник.
- Записать ограничения current-price point, скидок/локальности/дат; старые 14/20 не использовать.
- Критерий: полный source либо честный RANGE_SOURCE_UNAVAILABLE с рабочим ручным продолжением. Длительный поиск неподтверждённого API не блокирует остальные этапы.

**Q06. Постоянный ручной профиль.**

- Добавить additive storage в существующую tenant SQLite: versions, transaction, idempotency/CAS, allowlisted payload и quota.
- Проверить save/reopen/restart/update, другие owner/store/SKU/scheme и rollback.
- Критерий: N05 в repository/application слое, старые данные не меняются.

**Q07. Telegram-ввод и подтверждение комиссии.**

- Реализовать ввод одной цены/нескольких диапазонов, preview/confirm/cancel/edit и session-only режим.
- Привязать draft ticket к версии, владельцу, магазину и SKU; повтор и старая кнопка безопасны.
- Критерий: настоящий public route проходит N05 без ручного редактирования файлов.

**Q08. Snapshot и saved-plan интеграция.**

- Подключить resolver к новому сценарию; frozen profile/version/origin проходят capture/save/reopen/refresh.
- Добавить совместимый format version при необходимости; сохранить v1/v2 и explicit upgrade.
- Критерий: N06, неизвестный тариф не получает fallback на старую ставку текущей цены.

### C — расчёт цены

**Q09. Сравнение по ₽/шт.**

- Построить таблицу 2–10 явных вариантов поверх canonical forward и одного snapshot.
- Разделить значения/статусы/основания; сохранить baseline и выбранную цель при редактировании.
- Критерий: N01/N10, 0 новых source reads при смене цены/ДРР; неизвестный вариант не побеждает числом 0.

**Q10. Рекламные режимы и пороги компенсации.**

- Добавить одинаковую ДРР, отдельную ДРР и корректно поддерживаемый расход на единицу с обозначенным denominator.
- Реализовать non-worse/strictly-better thresholds через forward с округлением и конечной проверкой.
- Критерий: N02/N08/N11, включая недостижимую цель и зависимый от рекламы налог.

**Q11. Ограниченный набор кандидатов.**

- Добавить диапазон/шаг и обязательные тарифные границы в рамках limits; раскрывать фактически исследованный набор.
- Разделить результат сетки и недоказанный глобальный optimum.
- Критерий: N03/N04/N12, детерминированный лимит вычислений, без сетевых запросов.

**Q12. Целевая цена при скачках.**

- Проинвентаризировать старый solver; новые профили считать по покрытым сегментам и сравнивать валидные результаты.
- Старые single-rate contracts сохранить, неподдержанную область не вычислять старым бинарным поиском.
- Критерий: минимум для цели не теряется из-за разрыва; прямой forward подтверждает результат и соседнюю копейку.

**Q13. Лимит рекламы, sensitivity и batch consumers.**

- Найти все потребители смены цены и комиссии: ad cap, sensitivity, single/batch plan, mix, comparison/export.
- Применять один resolver/снимок там, где профиль поддержан. Иначе показывать явное ограничение и корректный старый режим с его origin.
- Критерий: разные экраны не используют разные комиссии одного варианта, кросс-докинг/налог не задваиваются.

**Q14. Числовая приёмка модуля C.**

- Прогнать N01–N06, N08, N10/N11 и существующие unit-price suites в изоляции.
- Зафиксировать exact result/ошибки/корректировки и реальные пределы поддержанного поиска.
- Критерий: числа и подписи проходят связанные проверки, без декларации полного инструмента до D–H.

### D — наблюдения

**Q15. Контракт наблюдения и истории цены.**

- Определить price declaration vs verified history, completed intervals/timezone, виды количества и source clocks.
- Описать способ получения фактической цены и ограничения по каждому полю, не приписывая текущую цену прошлому.
- Критерий: N07–N09 покрыты контрактами; missing history не маскируется ручным планом.

**Q16. Журнал и версии результата.**

- Additive repository/application для start/end/archive/note и immutable result versions; CAS/idempotency/quotas.
- Проверить duplicate start, overlap, restart, corrupt/future version и two-store isolation.
- Критерий: наблюдение долговременно и безопасно; не дублирует финансовую БД или planning revisions целиком.

**Q17. Read-only сбор по запросу.**

- Один bounded application flow собирает выбранные завершённые окна через существующие adapters.
- Реальный HTTP transport заменять fake в тестах; retries/пагинация/Performance polling входят в root budget.
- Критерий: нет requirement платной подписки, неизвестные поля и неподдержанные типы сохранены; live creds не нужны для инженерной приёмки.

**Q18. Нормализация сумм, единиц и рекламы.**

- Взвешенные агрегаты, dedup, mixed prices, date basis, corrections, ads revenue basis и no-double-count.
- Различать уже включённую рекламу в finance и дополнительный Performance evidence; не вычитать обе суммы.
- Критерий: N07–N09/N11; account totals не распределяются по SKU автоматически.

**Q19. Получение сопоставимой оценки.**

- Canonical fact использовать только при существующей достаточной полноте; иначе построить отдельно подписанную модель по наблюдавшимся входам или показать incomplete.
- Не превращать текущую/историческую себестоимость, cross-dock estimate или CPC-only в полный факт.
- Критерий: три основания раздела 6.2 не смешиваются, расчёт совпадает с соответствующим canonical контрактом.

**Q20. Полный Telegram цикл наблюдения.**

- Из сохранённого варианта открыть preview/start, карточку, сбор, завершение, заметки и историю результатов.
- Указание владельца о ручной установке цены хранить отдельно; ни один callback не вызывает Ozon mutation.
- Критерий: public start → collect → reopen → finish работает без raw JSON/ручных файлов; отсутствие данных даёт понятное продолжение.

### E — рекомендации

**Q21. Quality и comparability gates.**

- Проверять price history, окна, количества, basis, тариф/налог/расходы, overlap, полноту, свежесть и известные confounders.
- Выборку/дни показывать явно; configurable thresholds не выдавать за статистическую уверенность.
- Критерий: все причины сохраняются на экране и в payload; неподтверждённый вариант не получает verified label.

**Q22. Рейтинг и объяснение.**

- Выбрать max ₽/шт. среди сопоставимых вариантов, с равенством, отрицательной базой и корректными разницами.
- Отдельные рейтинги плановых допущений и наблюдений; ограничение «среди проверенных» обязательно.
- Критерий: N10 и примеры раздела 10; больше заказов не заменяет целевой критерий, causal claims отсутствуют.

**Q23. История, актуальность и обновление.**

- Новая редакция тарифа/результата не меняет исторического победителя молча; новое сравнение ссылается на конкретные версии.
- Reopen/cache/export source-free; явный refresh создаёт новое evidence без уничтожения старого.
- Критерий: повторное чтение стабильно, superseded/stale понятны, очистка cache не уничтожает durable records.

**Q24. Связать помощник целиком.**

- Путь SKU → тариф → сравнение → пороги → сохранение → наблюдение → рекомендация → возврат/следующий вариант.
- Для каждого incomplete состояния есть действие, которое использует прежний черновик и не сбрасывает ввод.
- Критерий: готовый пользовательский сценарий через production factory, без тестового прямого обхода handlers.

### F — завершённость

**Q25. Читаемый Telegram UX.**

- Компактные результаты, ₽/шт. как главный показатель, короткие причины, подробности отдельным действием, точная схема/identity.
- Обновить help/menu discovery и навигацию; старые entrypoints сохранить.
- Критерий: ни один обещанный переход не ведёт в заглушку; длинные ответы проходят splitter.

**Q26. Единые owner exports.**

- CSV/JSON сравнения, тарифного профиля и наблюдения из того же snapshot; версии/основания/неизвестность сохранены.
- Использовать существующий serializer/document transport; ошибки отправки управляемы.
- Критерий: экран и файл одинаковы, N12, нет source reads и произвольного расширения support JSON.

**Q27. Конкурентность и scope.**

- Старые/повторные callbacks, два параллельных сохранения, переключение магазина/SKU во время запроса, late responses, cache eviction.
- CAS проверяет metadata и payload там, где это требуется, а не только номер видимой страницы.
- Критерий: одна разрешённая запись, никакого cross-store результата, корректный конфликт без потери черновика.

**Q28. Лимиты и восстановление после сбоев.**

- Retry/429/timeout/cancellation/partial source, quotas, oversized input/export, обрыв транзакции.
- Локальные действия не блокируют API, источник вызывается один раз на разрешённый snapshot refresh.
- Критерий: N12 и fake-clock/attempt assertions; пользователь может повторить только неуспешный сбор.

**Q29. Persistence, privacy и restore.**

- Старая БД/планы читаются, новые таблицы включены в существующий backup/restore, raw/secrets не сохраняются в report payload.
- Выполнить N13 в новом synthetic root, проверить scopes и чтение после reopen.
- Критерий: нет разрушительной миграции или неограниченного роста данных, owner source не трогали.

### G — приёмка

**Q30. Сквозные пользовательские тесты.**

- Не менее трёх содержательных flows: автоматический подтверждённый тариф; manual fallback с двумя диапазонами; недостаточное наблюдение → допущение → доступная модель → сравнение.
- Включить store switch, restart, сохранение/экспорт и запрет Ozon mutation через public handlers.
- Критерий: реальные production composition contracts проверены fake источниками; тесты не зеркалят private helpers.

**Q31. Регрессии и сбои.**

- Связанные старые price/plan/tax/cross-dock/period/ad budget/backup/UI suites; исправить только подтверждённые регрессии.
- Проверить evaluation limits без случайных wall-clock thresholds и маленький bounded многократный цикл.
- Критерий: результаты и пределы записаны, тестовые source/data hashes сохранены.

**Q32. Документация и acceptance package.**

- Обновить user guide, CHANGELOG, CURRENT_STATE, TEST_MAP, ROADMAP; DECISIONS только по изменившимся архитектурным контрактам.
- Инструкция для владельца: новый SKU/выбор цены, ручной тариф, запуск наблюдения и сбор результата, как понимать limited recommendation.
- Критерий: один список внешних evidence; никаких requests keys/.env/необезличенных выгрузок. Неполученные данные не блокируют независимые проверки.

### H — готовность к независимому review

**Q33. Полные проверки актуального кода.**

- Полный pytest в изолированной среде, compile и diff checks; GitHub Actions на exact current head — Windows/Linux и Docker по действующему workflow.
- Если локальный полный запуск блокирует ACL, документировать actual failure и получить полный exact-head CI; не объявлять suite passed по выбранному подмножеству.
- Критерий: все обязательные checks зелёные, нет ignored failures или переносов результата на другой SHA.

**Q34. Собственный технический review и исправления.**

- Проверить diff по экономическим/tariff/date/scope/persistence/budget contracts; воспроизвести подтверждённые findings и исправить маленькими commits.
- После изменения кода повторить подходящие regressions и current-head CI.
- Критерий: self-review findings закрыты доказательствами. Это не выдаётся за независимое одобрение PR.

**Q35. PR и передача.**

- Открыть небольшие PR или ограниченный зависимый стек; dependency/base явно указаны, все созданные PR прикреплены к чату.
- Дать review package: touched contracts, fixtures N01–N13, risks, schema/backward compatibility, exact SHA/run links, доступные и неполученные owner evidence.
- Критерий: PR доступны для review и зелёные на текущих heads. Не merge/deploy/запускать реального бота. Не ждать реальных семи дней или ответа владельца для завершения инженерной передачи.

## 14. Работа автономно и восстановление после сокращения контекста

Работать последовательно до Q35, не завершать turn после каждого модуля и не просить разрешения на routine изменения в этом объёме. Короткие progress updates допустимы и нужны; они не являются остановкой выполнения.

После каждого этапа обновлять журнал:

- статус: NOT_STARTED / IN_PROGRESS / VERIFIED / VERIFIED_EXISTING / BLOCKED_EXTERNAL / BLOCKED_DECISION;
- base/head, время, изменённые файлы и краткий результат;
- точная команда/профиль, passed/failed/skipped и причина;
- что не проверено, фактические ограничения источников;
- следующий этап и краткий resume checklist.

При сокращении контекста прочитать журнал, проверить HEAD/status и продолжить с первого незавершённого доступного этапа. Не запускать заново завершённый аудит и не переносить результаты на новый SHA без основания.

Нельзя останавливаться только потому, что:

- нет автоматической полной тарифной сетки: реализовать согласованный manual fallback;
- нет подписки/исторической цены/CPO: сохранить ограничение и закончить поддерживаемую модель;
- для реального наблюдения не прошли семь дней: использовать синтетическую приёмку;
- требуется ещё один ограниченный adapter или backward-compatible migration, разрешённые этим ТЗ;
- завершён один модуль и удобно написать промежуточный финальный ответ.

Обратиться к владельцу только если требуется новое бизнес-правило: иной способ распределения неатрибутированных расходов, изменение цели, налоговой политики, read-only границы, доступ к реальным данным/платной услуге или неустранимый блокер без поддержанного fallback. Сначала закончить независимые этапы, сформулировать один конкретный вопрос и указать, что именно от него зависит.

## 15. Проверки и дисциплина Git

- Тесты — meaningful regressions контрактов и сквозных сценариев, не проверки совпадения строк кода и не обязательный новый тест для каждой документальной правки.
- Профиль этапа выбирать по изменённому поведению; не повторять большой suite без новых изменений/причины. Полный suite обязателен в Q33 и после затрагивающих его исправлений по риску.
- До запуска явно проверить root/storage/temp/credentials; не использовать owner `.env`, tracked data или его рабочий SQLite.
- Не менять ACL и не удалять чужие temp/review каталоги, не выполнять `reset --hard`, `clean`, blanket restore/stash/drop.
- Для commits использовать явный список файлов. Не `git add -A` в грязной папке. Документы и новые тесты не должны затянуть данные, locks и отчёты владельца.
- Не создавать по одному косметическому PR на каждый этап; рекомендуемые границы: тарифы+manual flow, price comparison+thresholds, observations+recommendation, acceptance при необходимости. Стек зависит от проверенных heads, не от неподтверждённых промежуточных деревьев.
- Ни один PR не должен требовать забытых untracked файлов для работы. Repo-relative paths в ТЗ не заменять machine-specific импортами.
