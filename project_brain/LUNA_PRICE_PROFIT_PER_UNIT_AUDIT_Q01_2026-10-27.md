## Отсутствующие контракты, которые требуется добавить

1. Чистый resolver диапазонов комиссии: точные границы в копейках, схема/магазин/SKU/дата, происхождение значения, конфликт/неизвестное состояние; точечную ставку нельзя распространять на диапазон.
2. Подтверждение tariff schedule: доступный официальный источник должен доказывать применимость к SKU и каждому интервалу; иначе ручной owner-confirmed профиль должен оставаться рабочим полноценным fallback.
3. Долговременная версия ручного профиля диапазонов с tenant isolation, idempotency/CAS, stale callback protection, audit provenance и редактированием без изменения старых frozen plan revisions.
4. Единое сравнение сценариев по `profit` в ₽ за успешную единицу через `UnitPriceScenarioService`; различимые assumption/evidence states; один source snapshot без запроса к источникам при правке цены/ДРР.
5. Рекламная компенсация: минимальные ДРР/расход на единицу для равенства и строгого улучшения baseline прибыли, с canonical rounding, точным финальным подтверждением и объяснённой базой ДРР.
6. Ограниченная сетка цен с явными найденными кандидатами и обязательным разбиением на tariff bands; максимум только среди проверенных сценариев.
7. Записываемые владельцем наблюдения своей цены и явно запрошенное чтение только завершённых дней; невозможность восстановить прошлую цену по текущей карточке; immutable snapshot/revision с quality gates и same-day/partial source states.
8. Recommendation, открываемая только при минимальном качестве данных; рекомендации остаются ограниченными наблюдавшимися сценариями и не обещают причинность/глобальную оптимальность.
9. Повторное открытие и изменение сохранённого плана, цены, тарифа и наблюдений после перезапуска; тот же revision/snapshot в Telegram и exports; additive backup/restore без доступа к live store.

## Числовые и эксплуатационные ограничения

- Seller price вводится в рублях с точностью до копейки; деньги по unit округляются до копейки ROUND_HALF_UP.
- Existing target parser: 2–5 цен, raw text ≤256 chars; target input ≤16 chars. Existing planner budget — до 128 forward calculations; advertising-cap — до 128 evaluations и 0.01 percentage-point grid. Новые диапазоны/поиск обязаны иметь собственные явные лимиты.
- Seller price/current FBO commission source — только current-price point. Fixed/ads inputs неполны, поэтому canonical fact comparison запрещён без подтверждённой сопоставимости всех обязательных составляющих.
- Не найденный официальный тарифный API и недоступная детализация не блокируют ручной путь; ни одна старая ставка 14%/20% не используется как default.

## Вывод Q01

Существующая архитектура уже предоставляет canonical forward engine, Telegram shell, tenant scoped saved-plan repository, bounded source snapshots и достаточные security/CAS primitives. Не хватает price-dependent fee resolver и durable tariff profile, profit-per-unit comparison/compensation threshold интеграции, а также отдельного owner-operated observation/recommendation cycle. Рабочая формула налога, сценарная изоляция, saved-plan engine, Ozon client, factual finance engine и экспортный транспорт дублироваться не должны. Плановые допущения и наблюдения логично хранить как additive сущности в существующей tenant planning SQLite; решение о конкретном schema ownership/CAS/versioning оформить в Q03.

Q01 не меняет runtime и не требует новых тестов: это read-only mapping. Изолированный baseline относящихся suites и hashes tracked data проверяются Q02.
