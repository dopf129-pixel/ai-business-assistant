## Проверенный пользовательский переход

Новая регрессия в
`tests/test_period_profit_analytics_runtime.py::test_public_report_flow_opens_exact_period_expenses_returns_refreshes_and_exports`
проходит через public handler и реальные Telegram runtime services:

1. Формирует прибыль за 01–31.08.2026, открывает подробности и экран полноты.
2. Переходит по предложенному действию во внешние расходы с теми же точными датами.
3. Видит кнопку возврата к тому же owner/store report snapshot.
4. Подтверждает полноту расходов; после возврата остаётся исходный отчёт.
5. Явно обновляет расчёт. Новый снимок показывает подтверждённую полноту; CSV экспортируется без третьего чтения источника.
6. Устаревшее действие отклоняется для другого владельца и другого магазина.

Наблюдаемый query-service счётчик: **1 запрос** на исходный расчёт, **0** на
детали/полноту/внешние расходы/возврат/экспорт, **1 новый запрос** на явное
обновление. Fake repository хранит только одну запись покрытия и не использует
файловую БД.

## Обнаруженный и исправленный дефект

При переходе из отчёта обработчик принимал статус истёкшего owner/store snapshot
за успешный контекст. Runtime расходов затем безопасно отклонял пустой период,
но владелец видел общую ошибку вместо причины устаревшего отчёта. Теперь handler
принимает только `PERIOD_PROFIT_EXTERNAL_EXPENSE_CONTEXT_READY`; expired,
чужой или межмагазинный callback не открывает форму расходов. Внешние расходы
сохраняют точный период и возвратный callback, а клавиатура добавляет его только
для валидного report token.
