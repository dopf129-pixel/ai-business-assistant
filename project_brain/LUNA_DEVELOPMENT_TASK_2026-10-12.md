## Обязательные продуктовые границы

1. Decision 036: Ozon остаётся read-only. Аналитика, рекомендации, локальные факты и неисполняемые черновики допустимы. Изменение цен/рекламы/поставок/карточек и другие Ozon business mutations исключены.
2. Денежный авторитет общей прибыли — полные account-level начисления. Формула сохраняется: `net_accrual + valid_committed_return_cogs - product_cost - configured_tax`; внешние расходы применяются существующим отдельным контрактом один раз.
3. По установленному пользователем правилу база налога — общая выручка минус баллы за скидки. Использовать действующий TaxService/политику магазина, включая режимы и minimum tax. Это правило конфигурации проекта, а не новая юридическая интерпретация.
4. `unknown != zero`: отсутствие данных, ошибки API, частичная пагинация и неопределённая классификация не создают нулевую сумму или подтверждение полноты.
5. Число строк реализации, финансовых операций, заказов, заказанных единиц и физических продаж — отдельные величины. Количество для COGS берётся из существующего доказательного контракта.
6. Identity архивного и текущего SKU подтверждается точным источником/явным фактом продавца, а не сходством названия. Подтверждение и отзыв должны оставаться доступными и изолированными по магазину.
7. Return COGS сохраняет цепочку quantity/identity → inventory → attribution/compensation → recognition → authorization → commit → final application. Новый seller-facing accounting commit control не входит в ТЗ.
8. Context, pending формы, кэш и результаты привязаны к `user + store + requested scope + period`. Смена магазина не переносит старый ввод или результат в новый магазин.
9. Рабочие данные, `.env`, ключи и сырые отчёты не включать в commits. Не применять `git restore/reset/clean` или общий stash к чужим изменениям ради получения чистого дерева.
10. Не заменять SQLite/JSON, core pipeline, task engine или существующую архитектуру новым framework. Такая замена требует Critical Review по AGENTS и отдельного решения владельца.

- Сохранять heartbeat, но вводить измеряемые бюджеты страниц, API calls, retries и времени optional enrichment. Бюджет исчерпан — enrichment неполный; доказанные основные деньги не теряются. Не выдавать частичный finance за полный.
- Общий срок регулировать кооперативно на границах запросов/циклов. `cancel asyncio.to_thread` не означает остановку worker; не освобождать защиту и не допускать позднюю запись, пока worker может работать.
- Старый результат явно связан со своим магазином/периодом и не подменяет новый запрос. Проверить двойные callbacks, смену магазина, исключения и завершение после timeout.
- Использовать request-local prefetch/кэши, существующие call budgets и diagnostics. Повторное открытие подробностей не пересчитывает отчёт; сравнение прошлого периода не повторяет текущий расчёт.

**Приёмка.** Fake clock и spy clients доказывают ограниченное число вызовов, один in-flight worker на одинаковый запрос и cleanup после failure. Недоступная сверка Performance не блокирует известную основную экономику. Зафиксировать фактические call counts/timing на контролируемой фикстуре; обещать live SLA только после live measurement.

**Точки входа.** `telegram_api_bot.py`, `period_profit_operation_diagnostics.py`, request/session/cache services, experimental enrichment, Ozon `_post`; stall/progress/parallel-read/previous-period tests. Не вводить новый job framework или постоянную очередь в этом пакете.

### P06. Внешние расходы через Telegram

**Результат.** Продавец добавляет внешний расход и подтверждает полноту периода кнопками в активном магазине.

- Кнопка «Внешние расходы»: список периода, «Добавить расход», «Подтвердить учёт за период», «Главное меню». Форма собирает дату, категорию, сумму и необязательное описание; перед сохранением показывает итог и явное подтверждение.
- Использовать `ExpenseRepository` и `PeriodProfitExternalExpenseEvidenceService`; сохранить существующие локальные скрипты. До первой версии включить one-off rows и coverage intervals. Recurring engine не входит в этот пакет.
- В пояснении отделить внешние затраты от уже учтённых Ozon удержаний. Не импортировать CPC/хранение/логистику повторно как внешние расходы.
- Не создавать coverage автоматически после добавления одной строки. Пустой подтверждённый период — известный ноль; пустой неподтверждённый — unknown. Для частичного покрытия показывать gaps и предварительный результат по внесённым расходам.
- Повтор подтверждения одного draft не создаёт второй расход. Чужие/устаревшие callbacks и смена магазина до подтверждения отклоняются.

**Приёмка.** Пустой полный/неполный период, частичные/пересекающиеся интервалы, два магазина, repeated callback, invalid/negative/NaN amounts и error записи проверены. Расход вычитается один раз существующим query contract. Отчёт не получает название «полная чистая прибыль», пока остальные material gaps остаются.

**Точки входа.** Expense repository/evidence/query, Telegram factories/adapters/keyboard/help; добавить meaningful flow tests и использовать существующий `tests/test_external_operating_expense_coverage_v1261_v1270.py` вместе с tenant storage suites.

### P07. Полнота расчёта и состояние возвратов

**Результат.** Кнопка «Полнота данных» объясняет, какие части прибыли доказаны и какие сведения нужны далее.

- Единый read-only экран по последнему точному store/period result: account finance, SKU/quantity, historical cost, tax policy, внешние расходы/coverage, return recovery; рекламная сверка — отдельно от полноты net accrual.
- Для каждого блока: подтверждено / частично / неизвестно / ошибка, период и краткая причина. Показывать известную базовую прибыль отдельно от недоказанного дополнения.
- Агрегировать Return COGS blockers из действующей canonical цепочки; counts кандидатов и units различать. Не создавать ещё один readiness gate. Первый блокер определяет доступную подсказку.
- Переходы к существующим себестоимости, SKU confirmation/revocation, состоянию возврата и новым внешним расходам. Для recognition/authorization/commit без seller-facing consumer показать ограничение, а не несуществующую кнопку применения.
- Ограниченная детализация точных return identities доступна только своему магазину. Main message краткий; malformed/stale evidence не получает confirmed claim.

**Приёмка.** Success, NON_SALEABLE, compensation, missing quantity, conflicting inventory, stale recognition/authorization, idempotent commit и partial candidate coverage дают правильную сводку без записей в accounting ledger. Counts раскрываются и сходятся с исходными records. Проверены tenant scope и повторное открытие без сетевого повторного расчёта.

**Точки входа.** `period_profit_query_service.py`, `period_profit_compact_response.py`, `PeriodProfitReturnCogsBlockerStageService`, existing coverage contracts и completion-status scenario list. Малый отдельный presentation/service extension допускается; classification: Architecture Review Required.

### P08. Сводка «На что обратить внимание»

**Результат.** On-demand кнопка показывает до пяти актуальных приоритетов магазина с основаниями и переходами к существующим отчётам.
