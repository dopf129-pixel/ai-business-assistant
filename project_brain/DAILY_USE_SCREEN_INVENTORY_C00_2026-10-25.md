- `telegram_progress_feedback.py` делит текст на фрагменты не более **3 800 UTF-16 units**, оставляет клавиатуру только на последнем сообщении и поддерживает supplementary-plane emoji.

## Схема экранов к C01–C05

### Основная финансовая сводка

1. Заголовок с точным периодом.
2. Ключевые подтверждённые суммы: выручка, начисления Ozon, налог, прибыль (явно «без себестоимости», если применимо), маржа.
3. Короткая метка полноты: подтверждено / частично / недоступно и одна наиболее важная причина.
4. Одно следующее действие, только если оно подтверждено snapshot `actions`.
5. Целевой объём основного сообщения — **1 500–2 500 символов максимум для варианта с ключевыми предупреждениями**; обычный ответ может быть короче, его не нужно дополнять служебным текстом.

Клавиатура на результате должна вести к scoped снимку: **Подробности**, **Полнота данных**, **Аналитика**, **CSV/JSON**. Действия с длинными деталями и экспортом не должны выполнять новые финансовые запросы. Если для подробностей потребуется новый callback, он должен содержать тот же непрогнозируемый view ID, owner/store scope и TTL, что существующий отчёт.

### Вторичные экраны

- **Подробности**: все категории, знаки, денежные доли, source/date basis, диагностические счётчики и объяснение, что не складывать повторно; длинные категории разбиваются по смысловым страницам. Ссылка «К расчёту» возвращает к тому же снимку.
- **Полнота данных**: текущая canonical projection и только доступные действия исправления; по возврату — исходная сводка того же периода.
- **Аналитика**: сравнение периода, что изменило прибыль, вклад SKU; текущие детализации остаются доступны.
- **Экономика магазина**: короткая сводка тех же ключевых сумм; детали категорий в отдельном cached view; live API diagnostics — из деталей и только по явному действию.
- **SKU и планирование цены**: сохранить выбранный SKU в callback scope; сначала итог одной успешной продажи/сценария, затем допущения, категории и методы; исторический план не пересчитывать молча.
- **Внешние расходы**: итог и coverage в начале; постраничные записи/gaps, затем подтверждённые действия добавления и возврата.

## Принципы перехода

- Передавать period, store и SKU через существующий scoped snapshot; при несовпадении магазина/ревизии безопасно отклонить устаревшее действие.
- Не терять детализацию: оставить её в snapshot callback и/или owner export, не в виде десятков строк основного ответа.
- Не смешивать суммы с разными date basis/grain, не заменять неизвестное нулём и не изменять финансовые формулы ради оформления.
- Новый запрос к Ozon делать только для явного «Обновить»/API diagnostic; открытие подробностей, истории и выгрузки читает текущий снимок.
- Считать лимит Telegram по UTF-16 units; пагинация работает по полным строкам, callbacks и клавиатура остаются на конечной странице.
