Новые пользовательские возможности:

1. **Обзор товаров**: выбрать ограниченную группу, увидеть подтверждённые проблемы и пробелы данных, отфильтровать и открыть товар.

5. **Диагностика через бота**: понять, почему результат неполный, получить безопасный обезличенный файл для разработчика и увидеть версию запущенного процесса.

## 6. Общие продуктовые и числовые контракты

### 6.1. Факты, допущения и неполнота

- Наблюдение Ozon, пользовательское допущение и рассчитанный сценарий — разные сущности с явным provenance.
- `unknown`, `unavailable`, `partial`, `stale`, подтверждённый ноль и ошибка различаются в данных и тексте.
- Отсутствующее поле не превращается в ноль. Пробелы рекламы/логистики не заполняются нулями автоматически.
- Фильтр и сортировка не повышают статус достоверности. Свежая дата запроса не делает свежими устаревшие source facts.
- Приоритеты нового обзора берутся из существующих решений; не придумывать новые коммерческие пороги/скоринг.
- Не обещать рост продаж/прибыли, минимальную цену на всём допустимом диапазоне или будущий тариф Ozon.

### 6.2. Финансы

- Канонические finance/TaxService/Return COGS calculations не переписывать.
- Историческое сравнение B/E из #697 остаётся самостоятельной базой; не смешивать его с планом успешной продажи.
- Планирование использует `UnitPriceScenarioService`; подбор цены — `UnitPriceTargetPlanningService`. Делегировать налог `TaxService`.
- Доля баллов: существующее взвешенное среднее за 28 завершённых дней по точному SKU либо явное ручное допущение. Это оценка будущего, не обещание размера скидки.
- Цена продавца — база планового revenue. Налоговый ввод и баллы передаются по текущему контракту; не вводить альтернативную налоговую формулу.
- FBO тариф — оценка. FBS не рассчитывать через FBO. Неподдержанную схему показывать отдельно.
- Целевая маржа проверяется по неокруглённому отношению результата к цене существующего калькулятора. Показанные 25,00% после округления не доказывают достижение 25%.
- Денежная сетка/границы и округление совпадают с текущим калькулятором. NaN/Infinity/bool/overflow и дробные копейки обрабатывать согласно его публичным parser contracts.
- По нескольким SKU не суммировать прибыль с одной единицы как прибыль магазина; среднее процентов не называть общей маржой. Прогноз объёма и весов продаж в этом пакете отсутствует.

### 6.3. Identity и scopes

- Для нового runtime обязательны точный владелец, активный store tenant, SKU/product/offer identity и generation.
- Decision reference может быть offer_id, даже если поле называется `sku`. Не передавать его как catalog SKU без однозначного разрешения.
- При неоднозначном каталоге/историческом SKU разрешены просмотр имеющихся фактов и объяснение ограничения; автоматическое открытие плана запрещено.
- Смена магазина, disconnect, новый выбор и истечение TTL инвалидируют связанные pending inputs/buttons. Старые события не меняют новый сценарий.
- На завершении медленного worker проверять operation ticket/generation. Старый ContextVar worker сам по себе не доказывает актуальность UI после переключения магазина.

| Чувствительность | Одна ось: 3–7 уникальных значений; две оси: до 7×7=49 ячеек |
| HTTP из фильтров/страниц/экспорта | 0; явное обновление — новый bounded запуск |
| Экспорт | До 2 MiB UTF-8 на файл; при превышении controlled отказ без молчаливого обрезания |
| Диагностические события в памяти | 256 последних событий, отдельный точный счётчик отброшенных |
| Telegram | Текст до 3 500 UTF-16 units на новый экран; callbacks до 64 UTF-8 bytes |

Лимиты — технические настройки первой версии. Не менять бизнес-правила ради того, чтобы поместить результат. При достижении лимита сохранять подтверждённые строки с явным `PARTIAL`; непросчитанные строки имеют причину `BUDGET_EXHAUSTED`, а не нулевые значения.

Долгий HTTP может завершиться позже желаемого времени; транспортный timeout ограничить оставшимся бюджетом. Не заявлять жёсткую остановку потока посреди внешнего вызова. Ожидание in-flight cache тоже ограничить оставшимся временем.

## 16. Автономная работа и восстановление контекста

После этапа не отправлять final с предложением «продолжить?». Обновить журнал, выполнить commit по allowlist и перейти к следующему этапу. Краткие commentary с результатами допустимы и нужны; они не являются остановкой работы.

Журнал `LUNA_LONG_RUN_PROGRESS_2026-10-17.md` содержит текущий модуль/этап, исходные и текущие SHA, dependency PR, сохранённые локальные изменения, итог этапа, фактические проверки, точные воспроизводимые команды, оставшиеся проблемы и **один следующий исполняемый шаг**.

Формат строки stage matrix:

`stage | NOT_STARTED/IN_PROGRESS/IMPLEMENTED/VERIFIED/BLOCKED | branch/base/head | files/contracts | checks + result | docs | blocker/next`

`IMPLEMENTED` не равно `VERIFIED`. Успешный старый SHA не принимает новый код. Каждое BLOCKED имеет конкретную причину/evidence и зависимые этапы. Если работает независимый модуль, продолжать его.

После compaction/возобновления сначала прочитать журнал, проверить фактическое дерево/HEAD, затем выполнить указанный next step. Не повторять выполненные этапы и не начинать аудит заново. Незакоммиченный code review пользователя важнее предполагаемого clean baseline.

При неудаче проверки: установить причину → воспроизвести → минимальное исправление → целевая регрессия → необходимая расширенная проверка. Не делать три одинаковых прогона с тем же падением. Внешнюю неизменившуюся ошибку допускается проверить с разумным backoff, затем работать независимо.

Обращаться к владельцу только при необходимости нового бизнес-правила, изменения границ данных/хранения, конфликте с пользовательской работой, запрещённой замене архитектуры или блокере, для которого исчерпаны безопасные альтернативы. Проблему незавершённого live evidence нельзя «решить» синтетическими данными в production; такой source остаётся unknown.

Если нужно завершить из-за лимита среды/контекста, сохранить handoff с точным next step, не объявляя завершённым пакет. Если всё готово раньше восьми часов, закончить по результату; новые несогласованные фичи ради времени не добавлять.

## 17. Проверки после этапов

1. Для pure builders — числовые эталоны, сравнение с настоящим existing calculator/TaxService, meaningful invariant/edge cases.
2. Для orchestration — injected clock, request counters и `Event` interleavings, write spies, реальные scope providers. Без timing sleep как условия успеха.
3. Для runtime — public handler/factory/adapters, fake Telegram/API, возвращаемые keyboard/file payload и stale callbacks.
4. Для файлов — semantic CSV/JSON roundtrip и adverse text; не snapshot-тест текста на каждую косметическую строку.
5. После изменения Python — compileall и diff check. После крупного модуля — полный `pytest` существующей конфигурации (`tests` и `app/tests`), CI нового SHA Windows/Linux и Docker.
6. Если локальный Windows pytest ограничен ACL: не изменять ACL/fixtures для обхода; использовать разрешённое изолированное окружение/чистый CI. Зафиксировать именно результат запуска и причину, не приписывать все падения ACL без доказательства.
7. На docs-only этапе новые runtime tests и повтор полного suite не нужны, если нет новых ошибок/изменений production; актуальная приёмка модуля всё равно требует зелёного CI его итогового PR SHA.

Обновлять CHANGELOG/CURRENT_STATE/TEST_MAP/ROADMAP и руководство пользователя после модуля. DECISIONS — только если действительно принято новое архитектурное решение; не создавать номера по догадке и не переоткрывать решения036–045.
